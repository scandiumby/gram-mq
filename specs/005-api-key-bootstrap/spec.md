# Feature Specification: Двухэтапный бутстрап API-ключа

**Feature Branch**: `005-api-key-bootstrap`

**Created**: 2026-10-17

**Status**: Implemented (2026-10-18)

**Input**: User description: "Нужно реализовать возможность задания API ключа в два этапа. Первый этап - локально запускается через uv команда, которая генерирует ключ и отдает от него hash. Далее должен быть эндпоинт, который по дефолту выключен сеттингом. Если пнуть этот эндпоинт, то он берет из другого значения этот хэш и добавляет ключ на сервер (таблица для хранения ключ уже есть в БД). Команда для генерации ключа уже есть, думаю, что для данной цели сделать другую команду."

## Контекст проблемы

Существующий путь выдачи API-ключа — `gram-mq key add` на сервере — требует
shell-доступа и доступа к БД: команда сама пишет строку (префикс + хэш) в
таблицу ключей. На контейнерных деплоях типа Amvera (один контейнер api+worker)
у оператора нет shell — доступны только переменные окружения панели и HTTP.
Возникает «курица и яйцо»: чтобы звать машинный API, нужен ключ; чтобы создать
ключ, нужен shell.

Решение — разделить выдачу на два этапа, не ослабляя конституционный
инвариант (Principle III): plaintext ключ никогда не пересекает HTTP и не
покидает локальную машину оператора. На сервер попадает только хэш — ровно
то, что и так хранится в БД.

1. **Этап 1, локально (uv)**: новая команда (отдельная от существующей
   `key add`) генерирует ключ, печатает plaintext один раз и рядом — одно
   готовое к копированию значение активации с материалом для сервера
   (префикс + хэш). БД и сервера не касается вовсе.
2. **Этап 2, на сервере**: эндпоинт активации, по умолчанию выключенный
   флагом в настройках. Оператор кладёт материал в значение настроек,
   включает флаг, «пинает» эндпоинт — тот читает материал из настройки и
   добавляет ключ в существующую таблицу. После операции флаг выключается;
   активированный ключ живёт в БД и продолжает работать.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Локальная генерация ключа без сервера (Priority: P1)

Как оператор, я запускаю локально через uv новую команду (отдельную от
существующей `key add`): она генерирует API-ключ того же формата и стойкости,
что и штатная выдача, печатает plaintext ключ один раз и рядом — одно
готовое к копированию значение активации, полностью описывающее материал для
сервера (префикс и хэш ключа). Команда не подключается к БД, не требует
серверных настроек и ничего не пишет на диск.

**Why this priority**: фундамент двухэтапной схемы; материал активации
проверяем отдельно (например, ручной вставкой) ещё до появления эндпоинта.

**Independent Test**: на машине без БД и без `GRAMMQ_DATABASE_URL` команда
завершается успехом и печатает ключ + значение активации; результаты двух
запусков различны.

**Acceptance Scenarios**:

1. **Given** локальная машина без доступа к серверу, **When** оператор
   запускает команду, **Then** печатается plaintext ключ (один раз), его
   префикс и значение активации с хэшем; код выхода — успех.
2. **Given** отсутствие `GRAMMQ_DATABASE_URL` и любых серверных настроек,
   **When** выполняется команда, **Then** она не завершается ошибкой
   настроек и не пытается открыть соединение с БД.
3. **Given** два последовательных запуска, **When** сравниваются результаты,
   **Then** ключи, префиксы и хэши различны.
4. **Given** сгенерированный материал, **When** хэш из значения активации
   сверяется существующей верификацией с plaintext ключом, **Then** проверка
   проходит: формат хэша совместим с действующей проверкой `X-API-Key`.

---

### User Story 2 - Активация ключа на сервере через выключаемый эндпоинт (Priority: P2)

Как оператор контейнерного деплоя без shell, я кладу значение активации из
US1 в настройку сервера, включаю флаг эндпоинта активации, дожидаюсь
применения настроек и «пинаю» эндпоинт одним HTTP-запросом: сервер читает
материал из настройки и добавляет ключ в существующую таблицу ключей. Ответ
подтверждает активацию и называет префикс — но не ключ и не хэш. После этого
я отключаю флаг; активированный ключ продолжает работать, потому что он
живёт в БД, а не в настройке.

**Why this priority**: завершает двухэтапный сценарий; без US1 бессмыслен,
но тестируем независимо (материал можно приготовить любым совместимым
способом).

**Independent Test**: с включённым флагом и настроенным материалом один
запрос активирует ключ; следующий запрос к машинному API с plaintext ключом
проходит авторизацию. После выключения флага ключ продолжает работать, а
эндпоинт перестаёт активировать.

**Acceptance Scenarios**:

1. **Given** флаг выключен (настройка по умолчанию), **When** оператор
   «пинает» эндпоинт, **Then** активация не происходит, никакой ключевой
   материал не обрабатывается, эндпоинт ведёт себя как недоступный.
2. **Given** флаг включён и материал задан, **When** приходит один запрос
   активации, **Then** в существующей таблице появляется строка (префикс +
   хэш из настройки) и ответ подтверждает активацию с префиксом.
3. **Given** ключ активирован, **When** клиент зовёт машинный API с
   `X-API-Key` = plaintext из US1, **Then** запрос авторизуется штатной
   проверкой — первый же запрос после активации.
4. **Given** флаг выключен после активации, **When** клиент повторяет запрос
   с тем же ключом, **Then** авторизация по-прежнему проходит: отключение
   эндпоинта не отзывает ключ.
5. **Given** флаг включён, но материал не задан или не распознаётся,
   **When** приходит запрос активации, **Then** отказ с понятной причиной; в
   таблицу ничего не пишется.

---

### User Story 3 - Повторные и посторонние вызовы безопасны (Priority: P3)

Как оператор, я не могу «сломать» состояние повторными вызовами: повторная
активация того же материала не создаёт дубль (понятный конфликт), конкурентные
вызовы не создают двух строк. Посторонний, которому известен адрес эндпоинта,
ничего не приобретает: он не знает plaintext ключа, поэтому активированный
ключ для него бесполезен, а наводнить таблицу чужими ключами он не может —
материал берётся из настройки, а не из запроса.

**Why this priority**: защищает целостность состояния и фиксирует
security-анализ схемы; не требуется для первого успешного прохода сценария.

**Independent Test**: дважды «пнуть» эндпоинт с одним материалом — второй
вызов даёт конфликт, в таблице одна строка; параллельные вызовы оставляют
ровно одну строку.

**Acceptance Scenarios**:

1. **Given** префикс из материала уже есть в таблице (включая отозванный),
   **When** повторно вызывается эндпоинт с тем же материалом, **Then**
   отказ-конфликт без изменения таблицы.
2. **Given** два одновременных запроса активации, **When** оба завершаются,
   **Then** в таблице ровно одна новая строка: один вызов успешен, второй —
   конфликт.
3. **Given** посторонний знает адрес эндпоинта и «пинает» его в окно
   активности, **When** происходит активация, **Then** в ответе нет ни
   plaintext, ни хэша (только факт и префикс), и воспользоваться ключом он
   не может.

---

### Edge Cases

- Флаг включён, значение материала пусто → активация невозможна, понятный
  отказ, ничего не пишется (US2, сценарий 5).
- Значение материала повреждено (не выделить префикс; хэш не в ожидаемом
  формате Argon2id) → отказ до любой попытки записи.
- Префикс активируемого ключа уже есть в таблице, в том числе отозванный
  (`revoked_at` заполнен) → конфликт; повторная активация не «воскрешает» и
  не перезаписывает ключ.
- Перезапуск процесса между установкой настроек и вызовом → материал
  читается из настройки на старте; после рестарта окно активации остаётся
  открытым, пока флаг включён.
- Оператор забыл выключить флаг после активации → новые активации того же
  материала невозможны (конфликт); выключение флага после операции — часть
  задокументированной процедуры.
- Сетевой сбой в момент вызова → оператор просто повторяет вызов: повтор
  либо успешно активирует, либо упирается в конфликт (идемпотентность
  результата — «не более одной строки на материал»).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Система ДОЛЖНА предоставлять новую локальную CLI-команду
  (отдельную от существующей `gram-mq key add`), генерирующую API-ключ того
  же формата и стойкости, что и штатная выдача.
- **FR-002**: Новая команда ДОЛЖНА выполняться без соединения с БД и без
  серверных настроек: отсутствие `GRAMMQ_DATABASE_URL` не является для неё
  ошибкой.
- **FR-003**: Новая команда ДОЛЖНА печатать plaintext ключ ровно один раз и
  одно готовое к копированию значение активации, полностью описывающее
  материал для сервера: префикс и хэш ключа.
- **FR-004**: Новая команда НЕ ДОЛЖНА ничего сохранять: ни записей в БД, ни
  файлов, ни логов с plaintext.
- **FR-005**: В настройках ДОЛЖЕН существовать флаг, включающий эндпоинт
  активации; значение по умолчанию — выключено.
- **FR-006**: В настройках ДОЛЖНО существовать значение с материалом
  активации (префикс + хэш из FR-003); оно секретное и не имеет значения по
  умолчанию.
- **FR-007**: Пока флаг из FR-005 выключен, эндпоинт активации ДОЛЖЕН быть
  недоступен и не выполнять никаких действий с материалом.
- **FR-008**: При включённом флаге и валидном материале один вызов эндпоинта
  ДОЛЖЕН добавлять ключ в существующую таблицу ключей (новые таблицы и
  миграции не вводятся): запись содержит префикс и хэш из настройки и не
  содержит plaintext.
- **FR-009**: Ответ об успешной активации ДОЛЖЕН содержать подтверждение и
  префикс ключа и НЕ ДОЛЖЕН содержать plaintext или хэш.
- **FR-010**: Повторная активация уже существующего префикса ДОЛЖНА
  завершаться понятным конфликтом без изменения таблицы; конкурентные вызовы
  не должны создавать дубликатов.
- **FR-011**: Активированный ключ ДОЛЖЕН немедленно проходить существующую
  проверку `X-API-Key` машинного realm-а, без дополнительных действий.
- **FR-012**: При включённом флаге и невалидном либо отсутствующем материале
  эндпоинт ДОЛЖЕН отказывать с понятной причиной, ничего не записывая.
- **FR-013**: Эндпоинт активации НЕ ДОЛЖЕН требовать существующей машинной
  авторизации (иначе бутстрап первого ключа невозможен); единственный
  переключатель его доступности — флаг из FR-005.
- **FR-014**: Plaintext ключ НИКОГДА не должен пересекать HTTP: запрос
  активации не несёт секретных данных; материал попадает на сервер только
  через настройки окружения, установленные оператором.
- **FR-015**: События активации (успех, конфликт, отказ по материалу)
  ДОЛЖНЫ логироваться без секретов — без plaintext и без хэша.
- **FR-016**: Существующая команда `gram-mq key add` и её поведение ДОЛЖНЫ
  остаться без изменений.

### Key Entities *(include if feature involves data)*

- **API-ключ (существующая сущность, без изменений)**: префикс (идентификатор
  для поиска), хэш ключа, время создания, отметка отзыва. Новых сущностей
  данных фича не вводит.
- **Флаг активации (новая настройка)**: булев переключатель доступности
  эндпоинта; не секрет; по умолчанию выключен.
- **Материал активации (новая настройка)**: значение, содержащее префикс и
  хэш предвычисленного ключа; секретное; без значения по умолчанию.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Оператор получает работающий API-ключ на деплое без
  shell-доступа и прямого доступа к БД, используя только локальную машину,
  настройки панели деплоя и один HTTP-запрос; вся процедура укладывается в
  несколько минут.
- **SC-002**: При настройках по умолчанию (флаг выключен) активация
  невозможна: никакая последовательность HTTP-запросов не добавляет ключ.
- **SC-003**: Plaintext ключ отсутствует в HTTP-трафике (запросах и
  ответах), настройках сервера, БД и логах — проверяемо тестами и
  инспекцией; в настройках и БД присутствует только хэш.
- **SC-004**: Первый же машинный API-запрос с активированным ключом успешен;
  после выключения флага ключ продолжает авторизоваться, а эндпоинт
  перестаёт активировать.

## Assumptions

- Целевой контекст — контейнерные/PaaS-деплои (Amvera): shell и прямой
  доступ к БД отсутствуют, переменные окружения и HTTP доступны; локально у
  оператора есть uv-окружение проекта.
- Настройки читаются на старте процесса: смена флага или материала требует
  применения настроек (редеплой/рестарт) — штатный цикл панели деплоя;
  «горячий» переворот флага без рестарта не вводится.
- Дополнительная аутентификация запроса активации не вводится: запрос ничего
  секретного не несёт, материал берётся из настройки, а активированный ключ
  бесполезен постороннему без plaintext. Эндпоинт включается только на окно
  операции.
- Одно значение материала на окно активации: для выдачи ещё одного ключа
  оператор повторяет двухэтапный цикл с новым материалом.
- Формат хэша — тот же Argon2id, что в существующей верификации; формат
  ключа — тот же, что в существующей выдаче (совместимость подтверждается
  действующим верификатором, US1 сценарий 4).
- Конституция, Principle III: инварианты сохранены — в БД только хэши,
  plaintext печатается один раз и не пересекает HTTP. Формулировку «ключ
  выдаётся только CLI на сервере» трактуем как «выдача — только CLI» с
  переносом места запуска: CLI у оператора локально, регистрация на сервере
  — через выключаемый по умолчанию эндпоинт активации хэша. Окончательную
  оценку соответствия фиксирует Constitution Check на фазе plan.
- URL эндпоинта, имена переменных окружения и кодирование значения активации
  (как именно префикс и хэш упакованы в одну строку) — решения фазы plan.
