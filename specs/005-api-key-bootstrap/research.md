# Research: Двухэтапный бутстрап API-ключа

**Date**: 2026-10-17 | **Status**: неясностей в спеке нет (все дефолты
зафиксированы в её Assumptions); здесь — решения плана.

## R1. Имя команды этапа 1

- **Decision**: `gram-mq key prepare` (новая подкоманда рядом с `key add`).
- **Rationale**: глагол «подготовить» точно отражает суть — команда готовит
  материал (ключ + значение активации), но ничего не регистрирует; пара
  `prepare`/`add` читается как «подготовить локально / добавить на сервере».
- **Alternatives**: `key generate` — не говорит, что ключ ещё не действует;
  `key issue` — конфликтует по смыслу с `key add`, который тоже «выдаёт»;
  отдельная группа `bootstrap key ...` — лишняя вложенность для одной
  операции.

## R2. Формат значения активации (перенос prefix + хэша)

- **Decision**: одна строка `prefix:хэш`, разделитель — первый `:`
  (`gmq_ab12cd34:$argon2id$...`). Формализуют `format_key_material()` /
  `parse_key_material()` в `api/auth.py` рядом с прочими примитивами ключа.
- **Rationale**: одно копирование из терминала в панель (FR-03 спеки);
  `:` не встречается ни в prefix (`[A-Za-z0-9_-]`), ни в Argon2id-кодировке
  (алфавит: base64 без padding + `$ , =`), поэтому сплит по первому `:`
  однозначен; строка остаётся читаемой в панели окружения.
- **Alternatives**: два отдельных поля настроек (prefix и хэш) — два
  копирования, рассинхрон и непонятная ошибка на эндпоинте; JSON — шумно
  для ручного переноса и требует экранирования в некоторых панелях;
  `prefix$хэш` — `$` уже смысловой символ Argon2-кодировки, парсер стал бы
  двусмысленным.

## R3. Валидация значения активации

- **Decision**: `parse_key_material` возвращает `None` при любом нарушении:
  нет `:`, более одного фрагмента после сплита по первому `:` (пустой хэш),
  prefix не матчит `^gmq_[A-Za-z0-9_-]{8}$`, хэш не начинается с
  `$argon2id$`, длина хэша > 128 (ширина колонки `key_hash` — String(128)).
- **Rationale**: проверка до записи (FR-012) гарантирует, что INSERT не
  упадёт по схеме; отказ единый, без различения причин наружу — материал
  секретен и не эхом в ответах/логах.
- **Alternatives**: детальные коды ошибок валидации — раскрывают структуру
  секрета в ответах и логах, пользы оператору не добавляют (в любом случае
  «пересоздай материал командой»).

## R4. Маршрут, метод и коды ответа эндпоинта

- **Decision**: `POST /bootstrap/api-key`, пустое тело. Ответы: успех —
  `201 {"status": "activated", "prefix": "..."}`; префикс уже существует —
  `409 {"detail": "api key already activated"}`; флаг выключен — `404`
  (маршрут «не существует»); флаг включён, но материал отсутствует или не
  прошёл валидацию — `503 {"detail": "bootstrap material missing or
  invalid"}` (одно сообщение на оба случая, без эха материала).
- **Rationale**: путь вне `/api/v1/*` и `/api/dashboard/*` — третий,
  административный surface (см. Constitution Check, IV); POST — операция
  меняет состояние, «пнуть» = один любой POST без тела и заголовков;
  201 — создана запись; 409 — идемпотентный конфликт повторного «пина»
  (FR-010); 404 при выключенном флаге — не раскрывает существование
  surface сканерами (FR-007, SC-002); 503 — «настройте и повторите»,
  честный сигнал оператору без утечки.
- **Alternatives**: GET-активация — семантически неверна (мутация) и
  уязвима к «пинку» из браузера/preload; 403 при выключенном флаге —
  подтверждает существование закрытого surface; 422/400 для битого
  материала — предлагает клиенту «исправить запрос», хотя чинить надо
  настройки сервера.

## R5. Порт активации и сборка адаптера

- **Decision**: в `api/app.py` — `class KeyActivator(Protocol)` с
  `async def activate(self, prefix: str, key_hash: str) -> bool`
  (True — вставлено, False — префикс уже есть) и frozen-снапшот
  `KeyBootstrap(enabled: bool, material: SecretStr | None)`. Продакшн-адаптер
  — замыкание в `api/main.py` (как `fetch` верификатора): INSERT через
  общую session factory, `IntegrityError → False`.
- **Rationale**: домен (`app.py`) остаётся без SQLAlchemy (конституция I);
  конкурентные вызовы закрываются PK prefix: ровно одна транзакция
  коммитится, проигравший получает IntegrityError → 409 (FR-010);
  тестируемость — FakeActivator, как FakeVerifier в тестах API.
- **Alternatives**: логика INSERT прямо в хендлере — домен узнаёт про
  SQLAlchemy; флаг/материал запрашивать у Settings через Depends — ломает
  явную сборку `create_app(...)` и стиль проекта (инъекция на сборке).
- **Уточнение 2026-10-18 (converge T016)**: фактическая форма порта —
  коллэйбл-алиас `KeyActivator = Callable[[str, str], Awaitable[bool]]`
  вместо Protocol-класса с `.activate`: живой прогон quickstart (T014)
  вскрыл дефект сборки (продакшн-замыкание из `api/main.py` не имело
  метода, юнит-тесты с FakeActivator-классом этого не видели). Коллэйбл
  следует образцу `KeyFetcher`/`fetch` из `api/auth.py`; семантика
  решения (True/False, инъекция, адаптер в `api/main.py`) неизменна.

## R6. Настройки

- **Decision**: два поля в `Settings`:
  `key_bootstrap_enabled: bool = False` и
  `key_bootstrap_material: SecretStr | None = None`
  (`GRAMMQ_KEY_BOOTSTRAP_ENABLED`, `GRAMMQ_KEY_BOOTSTRAP_MATERIAL`).
  Читаются на старте; смена — через env/редеплой (assumption спеки).
- **Rationale**: конституция Configuration — единый канал `GRAMMQ_*`;
  дефолт «выключено» верен во всех окружениях и версируется в коде;
  материал — SecretStr, чтобы `repr()` настроек и случайные логи не
  разбрасывали хэш (хэш не даёт входа, но и раскрывать его незачем);
  `None` — это «не настроено», а не дефолтное значение секрета: процесс
  спокойно стартует, отказ даёт эндпоинт (503), fail-fast здесь не нужен —
  выключенный бутстрап не ошибка.
- **Alternatives**: отдельный `BootstrapSettings`-класс — третья сущность
  ради двух полей, которые читает только api-процесс вместе с прочими;
  обязательный материал при включённом флаге (валидация на старте) —
  превратила бы «забытый материал» в отказ всего api-процесса вместо
  управляемого 503 на одном маршруте.

## R7. Активированный ключ и существующая верификация

- **Decision**: этап 1 использует те же `generate_api_key()` и
  `hash_key()` (argon2-cffi, дефолтные параметры), что и `key add`;
  серверная сторона хэш не пересчитывает — вставляет как есть.
- **Rationale**: активированный ключ немедленно проходит действующий
  `ApiKeyVerifier` (FR-011, US1 сценарий 4) без каких-либо изменений
  верификации; Argon2id на сервере в этом пути не выполняется вовсе —
  CPU-bound работы в запросе нет (конституция Asynchrony даже не касается
  его).
- **Alternatives**: свой формат «bootstrap-ключа» — вторая сущность ключа
  и вторая ветка верификации без выгоды; проверка хэша сервером
  (re-hash/verify) — невозможна по построению (plaintext у оператора) и
  не нужна.

## R8. Логирование и отказы по секретности

- **Decision**: логи — `api key activated prefix=...` (info),
  `api key bootstrap conflict prefix=...` (warning),
  `key bootstrap enabled but material missing or invalid` (error).
  Ни plaintext, ни хэш, ни материал в логи/ответы не попадают; prefix —
  не секрет (это lookup-идентификатор, возвращаемый и в ответе 201).
- **Rationale**: FR-014/FR-009 и SC-003; при этом prefix в логе делает
  аудит активации привязанным к строке БД.
- **Alternatives**: логировать материал «для отладки» — прямая утечка
  значения, эквивалентного содержимому БД, в логи PaaS.

## R9. Тестовая стратегия

- **Decision**: (а) unit `api/auth.py`: round-trip format/parse;
  parse отвергает мусор (нет `:`, битый prefix, не-Argon2id, >128).
  (б) unit CLI: `run_key_prepare` — материал = `prefix:хэш`, хэш
  верифицируется дешёвым hasher'ом, два запуска различны, БД нет вовсе
  (функция не принимает store). (в) unit эндпоинта (httpx ASGITransport +
  FakeActivator): 404 при выключенном/отсутствующем bootstrap, 201 + строка
  в FakeActivator при валидном, 409 при «уже есть», 503 на отсутствующем и
  битом материале, в ответах нет хэша. (г) сквозной тест «активировал —
  верифицировался»: FakeActivator пишет в dict, тот же dict кормит
  `ApiKeyVerifier` — US2 сценарий 3 без БД.
- **Rationale**: конституция Testing — публичные функции покрыты, БД не
  нужна для контрактного слоя; сценарий «курицы и яйца» проверяется
  композицией фейков; DB-гейт не требуется — INSERT-путь одинаков с
  `key add`, а конфликт дополнительно закрывается PK в существующих
  DB-тестах фичи 003.
- **Alternatives**: DB-gated тест активации — дублирует покрытие INSERT
  пути; опущен, quickstart даёт живую проверку на реальной БД.
