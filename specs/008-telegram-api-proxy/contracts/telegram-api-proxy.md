# Contract: Синхронный прокси Telegram Bot API (машинный realm)

**Spec**: FR-001…FR-010 | **Research**: R1, R4, R5, R6, R10 |
Документ для разработчика внешнего сервиса; общий каркас машинного
realm (ключ, базовый URL) — [http-api.md фичи 003](../../003-messaging-api-worker/contracts/http-api.md).

Назначение: вызов любого метода Telegram Bot API от имени бота с
результатом в том же HTTP-запросе. Токен бота никогда не покидает
сервер gram-mq — внешний сервис не получает, не хранит и не видит его.
Очередь `POST /api/v1/messages` (202 Accepted, доставка at-least-once)
остаётся единственным путём доставки новых сообщений; прокси — путь
вызовов, где результат нужен сейчас.

## POST /api/v1/telegram/{bot_slug}/{method}

Запрос:

```http
POST /api/v1/telegram/6789-arrakis-melange/getMe HTTP/1.1
X-API-Key: gmq_<43-char-base64url>
Content-Type: application/json

{}
```

- `bot_slug` — зарегистрированный бот (иначе 404);
- `method` — имя метода Bot API (`^[A-Za-z]{1,64}$`; иначе 404);
- тело — параметры метода в JSON **или** `multipart/form-data` для
  загрузки новых файлов (InputFile-параметры); оба формата проходят
  Telegram'у как есть, без перекодирования;
- `Content-Length`/фактический размер тела — до 50 МБ
  (GRAMMQ_TELEGRAM_PROXY_MAX_BODY_BYTES; 50 МБ — собственный потолок
  загрузок Bot API);
- иных заголовков прокси не требует и не интерпретирует.

## Ответы

Источник кода — кто его породил:

**От Telegram** (тело Telegram'а передаётся как есть, обёртка
`{"ok": …}`):

| Код | Условие | Тело |
|---|---|---|
| 200 | Telegram ответил `ok: true` | ответ Telegram (обёртка с `result`) |
| 429 | ограничение скорости | тело Telegram (внутри `parameters.retry_after`) + заголовок `Retry-After` |
| 400/403/404/5xx… | ошибка метода по вине параметров/чата/метода | тело Telegram (`error_code`, `description`) — исходный код и текст без изменений |
| 503 | Telegram отверг токен бота (401) | тело Telegram (в `error_code` виден исходный 401); чинит оператор gram-mq, повтор бессмысленен до починки |

**От gram-mq** (тело `{"detail": …}` — так отличимо от тел Telegram):

| Код | Условие |
|---|---|
| 401 | нет/неверен/отозван X-API-Key (единый ответ, без деталей) |
| 403 | метод в запретном списке ИЛИ не входит в разрешённый перечень — неразличимо |
| 404 | бот не зарегистрирован; также некорректный формат `bot_slug`/`method` |
| 413 | тело больше лимита (проверка до чтения по Content-Length и после) |
| 415 | Content-Type не `application/json` и не `multipart/form-data` |
| 422 | тело объявлено JSON, но не парсится; multipart без структурных границ |
| 502 | сеть до Telegram (нет ответа) |
| 503 | токен бота не готов (halves недоступны/не расшифровываются) |
| 504 | таймаут вызова (GRAMMQ_TELEGRAM_PROXY_TIMEOUT_SECONDS, дефолт 30 c) |

Семантика: прокси — чистый сквозной вызов. Никаких повторов, задержек и
постановок в очередь на стороне gram-mq: каждый исход — окончательный
для этого HTTP-запроса.

## Политика методов

**Запрещено всегда** (конфликтуют с управляемыми gram-mq потоками —
вебхуки и приём апдейтов): `getUpdates`, `setWebhook`, `deleteWebhook`,
`logOut`, `close`. Ответ 403 без обращения к Telegram; настройкой не
переоткрываются.

**Разрешено по умолчанию** (базовый перечень; расширяется оператором
gram-mq настройкой, списки могут отличаться на вашем инстансе):

```text
getMe                     sendMessage              answerCallbackQuery
answerInlineQuery         answerWebAppQuery        sendChatAction
editMessageText           editMessageCaption       editMessageReplyMarkup
editMessageLiveLocation   stopMessageLiveLocation  deleteMessage
getChat                   getChatMember
```

Метод вне перечня → 403; не входящие в базовый перечень методы (включая
`sendMessage` с мультимедиа и остальное семейство отправки новых
сообщений) оператор открывает по запросу потребности.

## Обязанности потребителя (обязательны)

1. **Анти-дубль: одно сообщение — один путь.** Новое текстовое сообщение
   без интерактива — очередь `POST /api/v1/messages` (at-least-once,
   переживает недоступность Telegram). Прокси — вызовы с
   результатом-сейчас: ответы на колбэки/inline-запросы (короткие окна
   Telegram), правки и удаление уже отправленного, действия, чтение, а
   также `sendMessage` для меню-ориентированных ботов (parse_mode и
   reply_markup недоступны очереди в её текстовом MVP). Дублирование
   одного смысла обоими путями запрещено; gram-mq не детектирует
   нарушение — дубль в чате останется незамеченным системой.
2. **Повторы — ваши.** На 429 ждите `retry_after` (тело/заголовок), на
   502/504/5xx Telegram — свой backoff. Прокси не повторяет никогда.
   Помните об идемпотентности: повтор `answerCallbackQuery` безвреден,
   повтор `editMessageText` перетирает более позднюю правку —
   последовательность правок держите у себя.
3. **Различение тел ошибок.** `{"ok": false, …}` — ответ Telegram
   (даже под нашим 503), `{"detail": …}` — ответ gram-mq. Код ответа
   достаточно проверять только после различения источника.

## Что отсутствует by design

- Никакого состояния вызовов, очередей и ретраев на стороне прокси;
  аудит-таблица вызовов отсутствует (журнал — логи оператора).
- Токен бота не возвращается ни в каком ответе, ошибке или заголовке.
- Синхронная отправка новых сообщений «с гарантиями очереди» — не
  существует: у прокси нет гарантий доставки, у очереди нет синхронного
  ответа (202 ≠ результат вызова).
- Статистика вызовов и интроспекция перечня методов по HTTP — нет;
  перечень — в этом документе и у оператора.
