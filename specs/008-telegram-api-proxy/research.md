# Research: Исходящий синхронный прокси Telegram Bot API

**Date**: 2026-11-22 | **Spec**: [spec.md](spec.md) | **Plan**: [plan.md](plan.md)

Фаза 0. Решения приняты по конституции v3.1.0, операторским сессиям
спеки (2026-11-22 и 2026-11-22 (2)), кодовой базе (`ports/telegram.py`,
`api/app.py` c `require_api_key` и паттерном условной регистрации,
`worker/bot_config.py` со `SplitFileBotConfig`/`TokenLookup`,
`adapters/http/deliverer.py` — образец httpx-адаптера, настройки) и
FR-001–FR-010 спеки. NEEDS CLARIFICATION в спеке нет — все развилки
сведены здесь в решения с отвергнутыми альтернативами.

## R1. Маршрут прокси: путь и идентификация

**Decision**: `POST /api/v1/telegram/{bot_slug}/{method}` — внутри
машинного realm (принцип IV), `X-API-Key` через существующую зависимость
`require_api_key`. `bot_slug` и `method` — сегменты пути; `method`
валидируется регуляркой `^[A-Za-z]{1,64}$` (имена методов Bot API —
camelCase-алфавит), несовпадение → 404 как у несуществующего маршрута.

**Rationale**: slug в пути даёт человекочитаемый журнал и единый
идентификатор бота по всему API (`/api/v1/messages` уже принимает его
телом); префикс `/api/v1/telegram/` собирает всю поверхность прокси в
одном подпространстве машинного realm — мониторинг и ACL оператора
(проксирующий nginx) могут закрыть или открыть её целиком, не задевая
`/api/v1/messages`. Жёсткая регулярка `method` отсекает трюки
обхода пути (`../`, слэши, закодированные символы) до какой-либо
проверки политики.

**Alternatives**: (а) `/api/v1/bots/{slug}/api/{method}` — сегмент `api`
в середине ничего не значит и путается с префиксом realm; (б) один
эндпоинт `/api/v1/telegram/call` с методом в теле — метод уходит из
URL: хуже для логов/мониторинга и ACL, тело перестаёт быть чистым
пасsthrough-грузом; (в) метод query-параметром — то же, плюс тела
`multipart` рядом с query выглядят неестественно; (г) вынести прокси в
отдельный URL-пространство `/proxy/*` — нарушение принципа IV (вызывающий
— машина с ключом, место ей — машинный realm; новых пространств спека
не вводит, FR-001).

## R2. Доменный порт: сырой passthrough, не типизированный вызов

**Decision**: `TelegramMethodCaller` (Protocol) в `ports/telegram.py`
рядом с `TelegramSender`:

```python
@dataclass(frozen=True, slots=True)
class TelegramMethodResponse:
    status: int          # HTTP-код ответа Telegram
    content_type: str
    body: bytes          # тело ответа Telegram как есть

class TelegramMethodCaller(Protocol):
    async def call_method(
        self, *, bot_token: str, method: str,
        content_type: str, body: bytes,
    ) -> TelegramMethodResponse: ...
```

Транспортные сбои (нет HTTP-ответа) — исключение `TelegramCallError`
(сиблинг `TelegramSendError`: `kind` = `"network" | "timeout"`), любой
полученный HTTP-ответ — результат, без интерпретации тела.

**Rationale**: спека фиксирует два «как есть» (FR-002 тело ответа,
Session (2) тело запроса без перекодирования) — порт обязан быть
байтовым конвейером; попытка типизировать параметры метода привязала бы
домен к эволюции ~200 методов Bot API, а парсинг тела сломал бы
multipart-passthrough. `bot_token` — параметр, а не состояние порта:
один объект обслуживает всех ботов (как `TelegramSender.send_text`).
Разделение «ответ есть / ответа нет» — ровно граница, которую
нужна эндпоинту для маппинга (R5): любой ответ Telegram — его код и его
тело; отсутствие ответа — наш шлюзовой код.

**Alternatives**: (а) обобщить `TelegramSender` (метод `call(...)`
рядом с `send_text`) — один порт растёт в два разных контракта
(очередевой воркер против синхронного прокси); сиблинги чище, а
предметная область одна — общий файл `ports/telegram.py`; (б) порт
принимает `dict` параметров — требует парсить JSON-тело (теряем
multipart и побайтовую идентичность) и знать схему каждого метода;
(в) порт возвращает `Any`-декодированный JSON — теряет content-type и
байтовую идентичность ответа, ломает «обёртку как есть» (FR-002).

## R3. Адаптер: httpx, не aiogram

**Decision**: `HttpxTelegramMethodCaller` в
`adapters/telegram/httpx_method_caller.py`: один общий `httpx.AsyncClient`
на процесс (`timeout=httpx.Timeout(settings.telegram_proxy_timeout_seconds)`,
`follow_redirects=False`), POST `https://api.telegram.org/bot{token}/{method}`
с заголовком `Content-Type` из запроса и сырыми байтами тела.
Исключения httpx (`TimeoutException` → `TelegramCallError("timeout")`,
`HTTPError`/`OSError` → `"network"`) оборачиваются с редакцией токена:
`str(exc).replace(token, "<redacted>")` — URL с токеном живёт в
сообщениях httpx-исключений. `aclose()` для выключения клиента.

**Rationale**: aiogram — высокоуровневый клиент типизированных методов;
«произвольный метод с сырым телом» — это в точности однострочный POST
httpx, который уже runtime-зависимость (007, BSD-3-Clause) с образцом
адаптера в `adapters/http/deliverer.py`. Единый клиент переиспользует
пул соединений (десятки вызовов/мин — соединение на процесс, не на
запрос). `follow_redirects=False`: редиректы от api.telegram.org —
неожиданность, которую прокси не должен следовать молча (пасsthrough
статуса).

**Alternatives**: (а) aiogram `Bot(...).__call__` с фейковым
`TelegramMethod` — контракция против его типизации ответов и сборка
метод-объекта из сырых байтов; кэш `Bot` по токену раздувается
экземплярами под прокси-ботов; (б) aiohttp напрямую — транзитивная
зависимость aiogram, объявлять прямую хрупко (то же обоснование, что
R6 спеки 007); (в) `urllib`/`requests` — запрещены конституцией
(Asynchrony).

## R4. Политика методов: константный запрет + белый список настройкой

**Decision**: два уровня, оба проверяются до обращения к Telegram.

1. `BANNED_TELEGRAM_METHODS = {"getUpdates", "setWebhook",
   "deleteWebhook", "logOut", "close"}` — константа кода в `api/app.py`,
   настройкой не переопределяется (FR-004: перечень фиксирован
   контрактом).
2. Белый список — настройка `GRAMMQ_TELEGRAM_PROXY_ALLOWED_METHODS`
   (CSV, регистронезависимое сравнение после нормализации), дефолт в
   коде: `getMe, answerCallbackQuery, answerInlineQuery,
   answerWebAppQuery, sendChatAction, editMessageText, editMessageCaption,
   editMessageReplyMarkup, editMessageLiveLocation,
   stopMessageLiveLocation, deleteMessage, getChat, getChatMember`.

Чистая функция `resolve_method_policy(method, allowed) ->
Literal["ok", "banned", "not_allowed"]`: запрещённый список проверяется
первым — задеть его расширением настройки нельзя (edge спеки).
Оба отказа — единый 403 `{"detail": "method not allowed"}` без
различения уровня. Дефолт перечня покрывает класс «результат нужен
сейчас»: реакции на апдейты в их окне (`answer*`), правка и управление
уже отправленным через очередь (`edit*`, `stop*`, `deleteMessage` —
анти-дубль про новые сообщения, не про правки), индикатор присутствия
(`sendChatAction`), контекст (`getMe`, `getChat`, `getChatMember`).

**Rationale**: операторская сессия выбрала default-deny с расширением
настройкой; фиксированный запретный список — защита управляемых потоков
(вебхуки CLI, приём 007), и он не может быть размыт конфигурацией.
Базовый перечень — минимальный набор,meaningful для потребителя без
`send*`: каждый новый метод требует осознанного решения оператора
(открыть или оставить очереди). CSV, а не JSON-список: env-переменные —
плоские строки, JSON в env — лишнее экранирование (конвенция
`key_bootstrap_material` — исключение с особым основанием: секрет).

**Alternatives**: (а) запретный список вместо белого (deny-list,
рекомендация specify-сессии) — отвергнут оператором: default deny
безопаснее, поверхность доступа растёт только явно; (б) белый список
константой кода без настройки — каждая новая потребность = правка кода и
деплой; оператор явно выбрал расширяемость; (в) пер-ботовая политика —
внешний сервис один на инстанс (Assumptions), различие политик не нужно;
г) различать коды 403 «запрещён» / 404 «не существует» — оракул
внутренней классификации без пользы потребителю; контракт документирует
оба перечня.

## R5. Маппинг ответов: passthrough кодов Telegram, две перекодировки

**Decision**: всё, что Telegram ответил, уходит вызывающему со своим
кодом и телом как есть (`Response(content=body, status_code=status,
media_type=content_type)`); два исключения и два дополнения:

| Ситуация | Код | Тело |
|---|---|---|
| Telegram `ok=true` | 200 | Telegram как есть |
| Telegram 429 | 429 | Telegram как есть + заголовок `Retry-After` (если Telegram прислал) |
| Telegram 401 (токен бота отвергнут) | **503** | Telegram как есть (`error_code: 401` виден в теле) |
| Telegram прочие (400/403/404/5xx…) | = код Telegram | Telegram как есть |
| Нет ответа: таймаут | 504 | `{"detail": "telegram timeout"}` |
| Нет ответа: сеть | 502 | `{"detail": "telegram unreachable"}` |
| Метод запрещён / вне перечня | 403 | `{"detail": "method not allowed"}` |
| Бот не зарегистрирован | 404 | `{"detail": "bot not found"}` |
| Токен не готов (`NotReady`) | 503 | `{"detail": "bot not ready"}` |
| Ключ неверен/отсутствует | 401 | `{"detail": "unauthorized"}` |
| Content-Type не JSON и не multipart | 415 | `{"detail": "unsupported content type"}` |
| Тело не парсится (JSON) / multipart без структуры | 422 | `{"detail": "invalid request body"}` |
| Тело больше лимита | 413 | `{"detail": "request body too large"}` |

**Rationale**: потребитель прокси — по сути клиент Bot API; коды и тела
ошибок Telegram (`{"ok": false, "error_code": 400, "description": …}`) —
его родная семантика «чья это вина и стоит ли повторять»: 400 — не
повторять (параметры), 429 — ждать `retry_after`, 5xx — можно повторить.
Оборачивание всего в 502 стёрло бы это различие и заставило парсить тело
ради решения о повторе. Единственная настоящая коллизия — 401: наш 401
значит «предъяви правильный X-API-Key», Telegram'овский — «токен бота
отозван»; склеивание лишило бы потребителя автоматической диагностики,
поэтому 401 от Telegram перекодируется в 503 (чинит оператор, повтор
бессмысленен — FR-008), а исходный `error_code` остаётся видим в теле.
503 — тот же класс, что `NotReady`: «бот неисправен на нашей стороне».
Различение наших и Telegram'овских ошибок — по форме тела
(`{"detail": …}` против `{"ok": …}`), зафиксировано контрактом.
`Retry-After` дублируется заголовком — стандартный машинный сигнал для
готовых HTTP-клиентов, у нас в теле он уже есть.

**Alternatives**: (а) всё успешное — 200, всё ошибочное — 502 с телом
Telegram: теряется семантика вины/повтора, тело обязательно парсить;
(б) полная нормализация в собственную обёртку ошибок: новый контракт
ошибок ради нуля новой информации, нарушение «как есть» (FR-002);
(в) наш 404 для неизвестного Telegram'у метода — метод уже прошёл белый
список, значит код перестал знать Bot API; passthrough 404 от Telegram
с его телом честнее (отличим от нашего `bot not found` по форме тела).

## R6. Тело запроса: Request без pydantic-схемы, два формата

**Decision**: хендлер принимает `Request`, проверяет `Content-Type`:
`application/json` (с суффиксами `+json`) → `json.loads(body)` как
валидация парсимости (содержимое не инспектируется); `multipart/form-data`
→ структурная проверка (параметр `boundary` в заголовке, тело непустое,
завершающая граница `--<boundary>--` присутствует); всё прочее → 415.
Лимит: `Content-Length` > лимита → 413 до чтения; после чтения —
повторная проверка длины (запросы без Content-Length). Дальше — байты
напрямую в порт, Telegram'у — без перекодирования.

**Rationale**: спека требует «без перекодирования» для обоих форматов и
отказ до Telegram для некорректного тела (edge кейсы; Session (2)).
pydantic-схема тела невозможна в принципе — тело произвольного метода
Bot API + multipart-файлы; starlette сам парсит multipart только при
`request.form()`, который потребляет и переупаковывает — нам нужны
исходные байты, поэтому структурная проверка границ вместо полного
разбора: она ловит битые тела (несформированный upload), а тонкие
ошибки состава полей всё равно диагносцирует сам Telegram (400
passthrough — лучшая диагностика, чем наша). Повторная проверка длины
закрывает chunked-запросы без Content-Length.

**Alternatives**: (а) не валидировать тело вовсе, полагаться на
Telegram — нарушает edge кейс спеки «отказ до обращения к Telegram»;
(б) полный разбор multipart (python-multipart) для валидации —
переупаковка или двойной парсинг ради проверки, которую Telegram делает
сам; (в) буферизация в temp-файл для больших тел — десятки ботов и
редкие вложения, 50 МБ в памяти процесса — норма (контейнер API уже
держит очереди в памяти соединений); усложнение без сценария.

## R7. Токен и сборка в API-процессе

**Decision**: продакшн-сборка (`api/main.py`) строит `SplitFileBotConfig`
тем же способом, что воркер (`SqlAlchemyBotRegistry(session_factory)
.fetch_half` + `bots_dir` + `parse_master_key`), и передаёт его в
`create_app` вместе с `HttpxTelegramMethodCaller` и разобранным
`frozenset` разрешённых методов. `TokenLookup` маппится: `NotRegistered`
→ 404 `bot not found` (единообразно с `/api/v1/messages`), `NotReady` →
503 `bot not ready`. В `create_app` маршрут регистрируется только при
инъекции обоих портов (`bot_config` + `method_caller`) — без них всё
`/api/v1/telegram/*` — 404; существующие вызовы `create_app` в тестах
предыдущих фич не меняются.

**Rationale**: модуль `worker/bot_config.py` — уже общее имущество
(импортируют воркер и CLI); третий импорт без переноса — минимальный
диф, а перенос пакета — шум в фиче, которая его не мотивирует.
Условная регистрация — установленный паттерн 007 (`/webhooks/*`):
машинный surface появляется только там, где собраны его зависимости.
Проверка `NotReady` перед вызовом Telegram обязательна: она же
предотвращает отправку заведомо битого токена (006: «No decryptable
pair — no messages are sent»).

**Alternatives**: (а) прокси спрашивает токен у воркера — новый
межпроцессный канал ради данных, которые API-процесс может собрать сам;
(б) кэш собранных токенов в памяти API — ускорение микросекундной
расшифровки ценой времени жизни секрета в памяти; отвергнуто (III:
минимальное пребывание в памяти); (в) перенести `BotConfig` в корень
пакета — правильная рефакторинг-цель, но вне зоны фичи; заметка на
будущее.

## R8. Журналирование: минимум полей, ноль секретов

**Decision**: одна строка на вызов в `gram_mq.api`-логгере:
`proxy bot=<slug> method=<method> status=<код вызывающему> dur=<ms>`
(+ класс исхода для отказов до Telegram: `denied=method_not_allowed`,
`denied=auth`, `not_ready`, …). Никогда не логируются: тело запроса,
тело ответа, токен, URL с токеном, значение X-API-Key. Длительность —
`time.monotonic()` вокруг вызова порта.

**Rationale**: FR-009 и US4: бот+метод+исход+длительность достаточно для
диагностики «почему колбэк не отвечен» и для оценки вклада прокси в
латентность (SC-001); всё сверх — утечка payload или секрета (III).
Отказы политики/авторизации логируются на warning (шум сканера виден),
успехи — на info.

**Alternatives**: (а) аудит-таблица — отвергнута оператором (Future
Enhancements); (б) debug-уровень с телами — включается оператором в
дебаге? Нет: тела не логируются ни на каком уровне (III записан для
вебхука 007 как абсолютный, распространяем).

## R9. Настройки: три поля, дефолты из внешних контрактов

**Decision**: `telegram_proxy_allowed_methods: str` (CSV; дефолт —
базовый перечень R4), `telegram_proxy_timeout_seconds: float = 30.0`,
`telegram_proxy_max_body_bytes: int = 52_428_800` (50 МБ). Все —
несекретные, дефолты верны в каждом окружении (Configuration);
`.env.example` документирует окна применения.

**Rationale**: 30 c таймаута покрывает медленные методы Bot API
(flood-паузы начинаются раньше; отдельные file-upload сценарии Telegram
держит до ~30 с), оставаясь меньше типичных upstream-таймаутов (nginx
60 c по умолчанию). 50 МБ — собственный потолок загрузок Bot API для
ботов: прокси не вводит предел теснее внешнего контракта, оператор может
сузить под свой профиль. Разбор CSV при сборке: элементы нормализуются
(trim, нижний регистр имён методов — сравнение регистронезависимое),
мусорные элементы (не-идентификаторы `^[A-Za-z]+$`) и пустая строка
целиком — ошибка старта с ясным сообщением (fail-fast, Configuration:
осмысленное значение или отказ). Отдельного выключателя прокси нет:
он — часть машинного realm, как `/api/v1/messages`; минимальная
поверхность по желанию оператора — перечень из одного `getMe`.

**Alternatives**: (а) отдельный включающий флаг
`GRAMMQ_TELEGRAM_PROXY_ENABLED` — пустой или полный перечень уже несёт
ту же семантику, дубль ручки; (б) JSON-массив в env — см. R4;
(в) дефолт таймаута 60 c — выше типичных upstream-прокси, превращал бы
наш 504 в чужой 504 (неопределённость для потребителя).

## R10. Контракт потребителя: анти-дубль и повторы

**Decision**: контракт (`contracts/telegram-api-proxy.md`) фиксирует
обязанности потребителя: (1) одно сообщение — один путь: доставка
нового сообщения — только очередь (`POST /api/v1/messages`, at-least-once),
синхронный прокси — только вызовы, где нужен результат сейчас (правки,
ответы на колбэки, действия, чтение); дублирование одного смысла обоими
путями запрещено и не детектируется системой; (2) повторы (429, 502/504,
5xx Telegram) — право и ответственность потребителя: темп и глубина
повтора на его стороне, прокси не ретраит никогда; (3) дедуп по
идентификаторам Telegram (`message_id`, `callback_query.id`) — на
стороне потребителя при его собственных ретраях (идемпотентность
конкретного метода Bot API — свойство самого Telegram).

**Rationale**: спека FR-006/FR-007: правило анти-дубля — контрактное,
не техническое; система не может надёжно детектировать «тот же смысл»
в очереди и в прокси (разные тела, разные времена) — попытка такого
детектора — ложные срабатывания и скрытая очередь внутри «синхронного»
прокси, разрушающая его семантику. Повторы — потребителю, потому что
только он знает, идемпотентен ли его вызов и какова цена дубля.

**Alternatives**: (а) технический запрет send*-семейства — отвергнут
оператором (Session 2026-11-22): перечень отправочных методов растёт с
Bot API, граница размыта (sendChatAction — не «сообщение», но send*);
контракт точнее кода; (б) скользящее окно дедупа вызовов на нашей
стороне — состояние в stateless-прокси и ложные блокировки правок;
(в) заголовок-маркер `Idempotency-Key` с дедупом на нашей стороне —
то же состояние + новый протокол; не нужно при очередевом пути доставки.
