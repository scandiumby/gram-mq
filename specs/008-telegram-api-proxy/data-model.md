# Data Model: Исходящий синхронный прокси Telegram Bot API

**Date**: 2026-11-22 | **Spec**: [spec.md](spec.md) | **Plan**: [plan.md](plan.md)

Правок схемы нет: прокси stateless (решение оператора, Session
2026-11-22 спеки) — ни миграций, ни таблиц, ни записей в очередях; БД
читается один раз на вызов (половина токена из реестра ботов,
существующая схема 006/007). Таблица аудита вызовов — Future
Enhancements. Ниже — доменные объекты, не имеющие хранилища, и их
инварианты.

## Доменные объекты порта (`ports/telegram.py`)

### `TelegramMethodResponse` — NEW: ответ Telegram как есть

| Поле | Тип | Назначение |
|---|---|---|
| status | `int` | HTTP-код ответа Telegram (200/4xx/5xx) — источник кода вызывающему (research R5) |
| content_type | `str` | Content-Type ответа Telegram (обычно `application/json`) |
| body | `bytes` | тело ответа побайтово: обёртка `{"ok": true, "result": …}` или `{"ok": false, "error_code": …}` — без парсинга и нормализации (FR-002) |
| retry_after | `float \| None = None` | секунды из заголовка Telegram `Retry-After` при 429 (нет/не число → None); добавлено на implement — контракт обещает эхо заголовка вызывающему, порт его несёт |

Инвариант: объект существует ⇔ Telegram дал какой-то HTTP-ответ; любое
отсутствие ответа (таймаут, обрыв) — исключение `TelegramCallError`
(`kind: "network" | "timeout"`), а не «пустой» результат — граница,
на которой эндпоинт переключается с passthrough на шлюзовые коды.

### `TelegramMethodCaller` — NEW: порт произвольного метода Bot API

```python
async def call_method(
    self, *, bot_token: str, method: str,
    content_type: str, body: bytes,
) -> TelegramMethodResponse
```

Сиблинг `TelegramSender` (фича 003) в том же файле: тот же домен
Telegram, другой контракт — исходящий текст очередевого воркера против
синхронного байтового конвейера прокси. Токен — параметр вызова, не
состояние порта: один объект обслуживает всех ботов. Тело и
Content-Type проходят без перекодирования (Session 2026-11-22 (2)):
`application/json` и `multipart/form-data` одинаково.

Адаптеры: `HttpxTelegramMethodCaller` (runtime, research R3) и fake
(тесты эндпоинта: запрограммированный ответ или исключение).

## Политика методов (не хранится: константа + настройка)

| Объект | Где живёт | Состав/семантика |
|---|---|---|
| `BANNED_TELEGRAM_METHODS` | константа кода (`api/app.py`) | `getUpdates`, `setWebhook`, `deleteWebhook`, `logOut`, `close` — конфликтуют с управляемыми потоками (вебхуки через CLI — 007, приём апдейтов самой системой). Настройкой не переопределяется (FR-004), проверяется первым |
| Разрешённый перечень | настройка `GRAMMQ_TELEGRAM_PROXY_ALLOWED_METHODS` (CSV → `frozenset[str]` при сборке) | базовый дефолт в коде — research R4; расширение без правки кода (FR-005); пересечение с запретным списком не расширяет ничего (чистая функция `resolve_method_policy` возвращает `banned` раньше `not_allowed`) |

Верdict политики — `Literal["ok", "banned", "not_allowed"]`; оба отказа
недоступности неразличимы для потребителя (единый 403), перечни
документированы контрактом.

## Сущности с состоянием, которых у фичи нет (и почему)

- **Вызов прокси** — событие журнала (логи `bot + method + статус +
  длительность`), не строка таблицы: постоянное хранение истории вызовов
  не входит в фичу (FR-009, решение оператора). Расследование «кто что
  звал» — уровнем логов; аудит-таблица — Future Enhancements со своей
  миграцией.
- **Состояние вызова** — отсутствует по семантике: прокси не ретраит и
  не резолвит (FR-002), промежуточных статусов не бывает; «состояние»
  вызова живёт у вызывающего (его HTTP-клиент) и в Telegram.
- **Очередные записи** — не создаются ни при каком исходе прокси-вызова:
  пути очереди (001/003/007) не пересекаются с прокси (конституция II,
  SC-004).

## Настройки (канал `GRAMMQ_`, класс `Settings`)

| Переменная | Тип/дефолт | Секрет | Потребитель |
|---|---|---|---|
| GRAMMQ_TELEGRAM_PROXY_ALLOWED_METHODS | str = CSV базового перечня (R4) | нет | сборка api/main.py → frozenset → create_app |
| GRAMMQ_TELEGRAM_PROXY_TIMEOUT_SECONDS | float = 30.0 | нет | HttpxTelegramMethodCaller (httpx.Timeout) |
| GRAMMQ_TELEGRAM_PROXY_MAX_BODY_BYTES | int = 52_428_800 (50 МБ — потолок загрузок Bot API) | нет | эндпоинт прокси (413 до чтения по Content-Length и после чтения) |

Инварианты: все три — несекретные, дефолты верны в каждом окружении;
разбор CSV — fail-fast на мусор/пустоту (research R9); больше никаких
новых настроек фича не вводит (включение — наличием машинного ключа и
собранных портов, как у всего машинного realm).
