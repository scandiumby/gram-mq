# Feature Specification: Исходящий синхронный прокси Telegram Bot API

**Feature Branch**: `008-telegram-api-proxy`

**Created**: 2026-11-22

**Status**: Implemented (2026-11-22)

**Input**: User description: "Фича 008: исходящий синхронный прокси Telegram Bot API. Внешний (нестабильный) сервер никогда не получает bot token — все вызовы Telegram API идут через наш прокси-эндпоинт на стабильном сервере (решение 007, spec.md:92-96). Очередь исходящих остаётся основным путём; прокси — для вызовов, где боту нужен результат сразу (getMe, answerCallbackQuery, editMessageText, sendChatAction). Синхронная семантика: 200 с JSON-ответом Telegram либо код ошибки, в отличие от очереди (202 Accepted). Правило анти-дубля: одно сообщение — либо через очередь, либо через прокси, никогда оба пути; документируется контрактом потребителя. Без ретраев на стороне прокси. Токен — из существующего сплит-хранилища (006): NotRegistered → 404, NotReady → 503-класс. Машинный realm /api/v1/* с X-API-Key. Открытые вопросы: белый список методов vs все, кроме запрещённых (getUpdates, setWebhook, deleteWebhook, logOut, close — запрещены обязательно); судьба sendMessage; маппинг ошибок; логи vs таблица аудита; лимиты (таймаут, размер тела); форма роута и ответа."

## Clarifications

### Session 2026-11-22 - specify: решения оператора (обязательны для плана)

Даны оператором явно при создании спеки; закрывают три критичных
открытых вопроса, остальные закрыты MVP-дефолтами в Assumptions.

- Q: Политика доступа к методам Bot API через прокси? → A: белый
  список с расширением настройкой (default deny): через прокси по
  умолчанию разрешены только явно перечисленные методы; перечень
  расширяется оператором настройкой системы без изменения кода.
  Запрещённые методы (FR-004) недоступны всегда — расширение на них не
  действует. Базовый перечень разрешённых методов версионируется в
  коде; точный состав — этап плана.

### Session 2026-11-22 (2) - clarify: формат тела вызова

- Q: Какой формат тела запроса поддерживает прокси — только JSON или
  также multipart для загрузки новых файлов? → A: оба: параметры
  вызова передаются JSON-телом, а загрузка новых файлов
  (InputFile-параметры Bot API) — multipart-телом; оба формата прокси
  пропускает Telegram'у как есть, без перекодирования. Лимит размера
  тела задаётся с учётом multipart-загрузок (значение — этап плана).
- Q: Отправка новых сообщений (sendMessage и семейство) через прокси?
  → A: технически не запрещается — только контрактным правилом
  анти-дубля (FR-006/FR-007): одно сообщение — либо через очередь
  (фичи 001/003), либо через прокси, никогда оба пути; обязанность
  потребителя, документирована контрактом.
- Q: Журналирование вызовов прокси? → A: только логи, как журнал 007
  (бот, метод, исход, длительность — без тел запросов и токенов);
  прокси без состояния, миграций схемы нет; таблица аудита вызовов —
  Future Enhancements.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Синхронный вызов метода Bot API (Priority: P1)

Как внешний сервис-владелец ботов, я вызываю метод Telegram Bot API от
имени своего бота через эндпоинт системы: передаю машинный ключ,
идентификатор бота (slug), имя метода и параметры вызова — и получаю
ответ Telegram сразу, в том же HTTP-запросе. Это позволяет боту
реагировать мгновенно там, где результат нужен сразу: подтверждать
колбэки (у answerCallbackQuery короткое окно ответа), править текст
сообщений, показывать статус «печатает», проверять себя (getMe).

**Why this priority**: это единственный синхронный путь внешнего
сервиса к Bot API; очередь исходящих (фичи 001/003) принципиально
асинхронна (ответ после постановки) и на эти случаи не рассчитана; без
прокси колбэки остаются без ответа в своё окно.

**Independent Test**: зарегистрировать бота, выдать машинный ключ и
выполнить через прокси getMe и answerCallbackQuery — ответ Telegram
возвращается вызывающему сразу, в очередях не появляется ничего; вызов
с неверным ключом и вызов для незарегистрированного бота отвергаются.

**Acceptance Scenarios**:

1. **Given** зарегистрированный и готовый бот и действительный машинный
   ключ, **When** внешний сервис вызывает через прокси метод с
   корректными параметрами и Telegram отвечает успехом, **Then**
   вызывающий получает ответ Telegram как есть с кодом успеха — в том
   же запросе, без постановки в какую-либо очередь и без повторов на
   стороне системы.
2. **Given** Telegram отвечает на вызов ошибкой (например, chat not
   found), **When** прокси получает её, **Then** вызывающий получает
   распознаваемый отказ с кодом и описанием ошибки от Telegram.
3. **Given** вызов без машинного ключа или с неверным значением,
   **When** система проверяет его, **Then** следует единый
   недифференцированный отказ авторизации — как во всём машинном
   пространстве, до какого-либо обращения к Telegram.
4. **Given** вызов для бота, отсутствующего в реестре, **When** система
   проверяет его, **Then** следует отказ «бот не найден», единообразный
   с прочими эндпоинтами, обращения к Telegram нет.
5. **Given** бот зарегистрирован, но его токен недоступен для
   использования (не готов), **When** приходит вызов, **Then** следует
   ретраебельная ошибка конфигурации бота, без обращения к Telegram.

### User Story 2 - Токен не покидает стабильный сервер (Priority: P1)

Как оператор стабильного сервера, я уверен: внешний (нестабильный)
сервер не получает и не хранит bot token ни в каком виде — все
обращения к Telegram происходят со стабильного сервера. Даже полная
компрометация внешнего сервера не раскрывает токены ботов: они не
пересылаются, не отражаются в ответах, логах и сообщениях об ошибках.

**Why this priority**: это мотивация самой фичи — граница доверия
проходит между стабильным и нестабильным сервером; без неё прокси
бессмыслен (внешний сервис мог бы звать Telegram напрямую).

**Independent Test**: прогнать прокси всеми путями (успех, ошибки
Telegram, сетевые сбои, ошибки конфигурации) и убедиться, что ни в
одном ответе вызывающему, ни в одной записи журнала, ни в одном
сообщении об ошибке нет токена и его производных.

**Acceptance Scenarios**:

1. **Given** любой вызов прокси, **When** он обрабатывается — успешно
   или с любой ошибкой, **Then** токен не появляется ни в ответе
   вызывающему, ни в журнале, ни в сообщениях об ошибках.
2. **Given** внешний сервер скомпрометирован и располагает машинным
   ключом, **When** злоумышленник исследует все доступные ему ответы,
   **Then** он не может восстановить токен ни одного бота и не может
   обращаться к Telegram от имени ботов напрямую.

---

### User Story 3 - Контроль методов: защита управляемых потоков и разрешённый перечень (Priority: P2)

Как оператор, я рассчитываю: прокси не даёт внешнему сервису сломать
управляемое системой состояние. Методы, конфликтующие с механизмами
системы, недоступны через прокси: getUpdates (конфликтует с вебхуками —
приёмником апдейтов теперь является сама система, фича 007, а Telegram
отвечает на getUpdates отказом при активном вебхуке),
setWebhook/deleteWebhook (вебхуками управляет CLI оператора),
logOut/close (переводят бота в режим polling). Остальные методы по
умолчанию закрыты: прокси открывает только перечень методов, явно
разрешённый оператором (базовый дефолт — в коде), и оператор расширяет
его настройкой, не меняя код.

**Why this priority**: один вызов внешнего сервиса мог бы незаметно
для оператора сломать приём апдейтов, а открытый без перечня прокси —
расширить поверхность доступа сверх необходимого; но это защита
поверх основной ценности (US1/US2), поэтому P2.

**Independent Test**: вызвать каждый запрещённый метод через прокси —
все отвергаются без обращения к Telegram, состояние вебхуков и
управляемость CLI после попыток не изменяются; вызвать метод вне
разрешённого перечня — отказ; расширить перечень настройкой — метод
становится доступен.

**Acceptance Scenarios**:

1. **Given** внешний сервис вызывает запрещённый метод, **When**
   система проверяет его, **Then** следует явный отказ «метод
   запрещён» без обращения к Telegram.
2. **Given** попытки вызвать запрещённые методы, **When** они
   отвергнуты, **Then** состояние вебхуков и настройки приёма апдейтов
   ботов не изменяются.
3. **Given** метод, не входящий в разрешённый перечень, **When**
   внешний сервис вызывает его, **Then** следует отказ без обращения к
   Telegram.
4. **Given** оператор расширил разрешённый перечень настройкой,
   **When** внешний сервис вызывает добавленный метод, **Then** метод
   доступен обычным порядком; попытка расширить перечень на
   запрещённый метод (FR-004) на него не действует.

### User Story 4 - Эксплуатация и настройка прокси (Priority: P3)

Как оператор, я вижу вызовы прокси в журнале — кто (бот), что (метод),
чем закончилось и как долго шёл вызов — без тел запросов и токенов; я
настраиваю таймаут вызова и предельный размер тела, не меняя код.

**Why this priority**: диагностика «почему колбэк не отвечен» без
журнала вызовов дорога; таблица аудита и эндпоинты статистики — вне
MVP (Future Enhancements).

**Independent Test**: выполнить серию вызовов (успешные, ошибочные,
запрещённые) и найти каждый в журнале по боту, методу и исходу;
изменить настройку таймаута и убедиться, что она применяется.

**Acceptance Scenarios**:

1. **Given** серия вызовов с разными исходами, **When** оператор читает
   журнал, **Then** каждый вызов виден как бот + метод + исход +
   длительность; тела вызовов и токены в журнале отсутствуют.
2. **Given** вызов дольше настроенного таймаута, **When** срок
   истекает, **Then** вызов обрывается, вызывающий получает
   распознаваемую ошибку таймаута.
3. **Given** запрос с телом больше предельного размера, **When**
   система проверяет его, **Then** следует отказ до какого-либо
   обращения к Telegram.

### Edge Cases

- Telegram недоступен (таймаут, обрыв сети) → вызывающий получает
  распознаваемую ошибку шлюза не дольше настроенного таймаута; прокси
  не ждёт дольше и не повторяет сам — повтор остаётся решением
  потребителя.
- Telegram отвечает ограничением скорости (429) → вызывающий получает
  отказ с параметром повтора (retry_after); прокси не выжидает и не
  повторяет.
- Telegram отвергает токен (отозван у BotFather) → ошибка конфигурации
  бота: ретраебельная для оператора (починить токен), бессмысленная
  для повторов потребителем; токен в ошибке не раскрывается.
- Потребитель повторяет свой вызов (клиентский ретрай) → прокси —
  чистый сквозной вызов: повтор выполняется как новый вызов;
  идемпотентность конкретных методов — свойство самого Bot API,
  результаты не кэшируются.
- Потребитель нарушил анти-дубль (одно сообщение ушло и в очередь, и
  через прокси) → возможен дубль в чате; система не детектирует и не
  предотвращает это на уровне доставки — правило носит контрактный
  характер (обязанность потребителя).
- Одновременные вызовы одного бота через прокси → прокси без
  состояния: вызовы независимы, конкуренции за очередь нет.
- Метод не входит в разрешённый перечень → отказ без обращения к
  Telegram; после расширения перечня настройкой метод доступен
  обычным порядком.
- Расширение перечня задело запрещённый метод (getUpdates,
  setWebhook, …) → запрещённые методы недоступны всегда: расширение на
  них не действует (FR-004 приоритетнее FR-005).
- Тело вызова не является корректным JSON и не является валидным
  multipart → отказ с ошибкой запроса до обращения к Telegram.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Система MUST предоставлять прокси-эндпоинт в существующем
  машинном пространстве URL: идентификатор бота (slug) и имя метода —
  параметры маршрута, параметры вызова — тело запроса; авторизация —
  тот же машинный ключ (`X-API-Key`), что и для остальных машинных
  эндпоинтов, с единым недифференцированным отказом для неверного
  ключа. Новых URL-пространств фича не вводит. Тело вызова — JSON или
  multipart (загрузка новых файлов); оба формата пропускаются
  Telegram'у как есть, без перекодирования.
- **FR-002**: Прокси MUST быть синхронным сквозным вызовом: при успехе
  вызывающий получает ответ Telegram (JSON как есть) с кодом успеха —
  в том же HTTP-запросе; без постановки в очередь, без повторов и без
  выжидания на стороне системы.
- **FR-003**: Токен бота MUST собираться из существующего сплит-хранилища
  (конфигурация ботов) только на время вызова и только в памяти
  процесса: незарегистрированный бот → единообразный «бот не найден»;
  недоступный для использования токен → ретраебельная ошибка
  конфигурации бота.
- **FR-004**: Система MUST запрещать через прокси методы, конфликтующие
  с управляемыми ею потоками: getUpdates, setWebhook, deleteWebhook,
  logOut, close — явным отказом «метод запрещён» без обращения к
  Telegram; перечень запрещённых методов фиксирован контрактом.
- **FR-005**: Политика остальных методов — белый список с расширением
  настройкой: по умолчанию через прокси разрешены только методы из
  перечня с базовым дефолтом в коде (минимальный набор синхронных
  вызовов внешнего сервиса; точный состав — этап плана); перечень
  расширяется настройкой системы без изменения кода. Методы,
  запрещённые FR-004, недоступны всегда — расширение перечня на них не
  действует. Метод вне перечня отвергается без обращения к Telegram.
- **FR-006**: Отправка новых сообщений (sendMessage и семейство)
  через прокси технически не запрещается; их использование
  регламентируется контрактным правилом анти-дубля (FR-007).
- **FR-007**: Контракт потребителя MUST документировать правило
  анти-дубля: одно сообщение — либо через очередь исходящих (фичи
  001/003), либо через прокси, никогда оба пути; а также обязанности
  потребителя по повторам (429, сетевые сбои — решение и темп повтора
  на его стороне).
- **FR-008**: Ошибки MUST отображаться вызывающему распознаваемо и без
  раскрытия токена: недоступность Telegram (таймаут, обрыв) → ошибка
  шлюза; ограничение скорости Telegram → отказ с параметром повтора;
  ошибки Telegram → вызывающий видит код и описание от Telegram;
  недоступный токен → ретраебельная ошибка конфигурации бота.
  Конкретные HTTP-коды — этап плана.
- **FR-009**: Система MUST журналировать каждый вызов прокси: бот,
  метод, исход (успех/класс ошибки), длительность — без параметров
  вызова и без токена; постоянное хранение истории вызовов (таблица
  аудита) в фичу не входит.
- **FR-010**: Таймаут вызова и предельный размер тела запроса MUST быть
  настройками системы с дефолтами в коде и меняться без изменения кода
  (конвенция GRAMMQ_-настроек; имена — этап плана).

### Key Entities *(include if feature involves data)*

- **Вызов прокси (событие журнала)**: бот (slug), имя метода, исход
  (успех или класс ошибки), длительность; параметров вызова и токена
  не содержит. Прокси без состояния: сущностей в хранилище фича не
  добавляет.
- **Политика методов (контракт и настройка)**: перечень запрещённых
  методов Bot API (FR-004) фиксирован контрактом, виден потребителю;
  перечень разрешённых — настройка системы с базовым дефолтом в коде.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Успешный вызов через прокси возвращает вызывающему ответ
  Telegram без изменений; накладные расходы системы сверх самого
  вызова Telegram не превышают 1 секунды при доступном Telegram.
- **SC-002**: Во всех ответах вызывающему, записях журнала и сообщениях
  об ошибках прокси отсутствует bot token и его производные —
  проверяется сквозным прогоном всех путей (успех, ошибки Telegram,
  сетевые сбои, ошибки конфигурации).
- **SC-003**: Каждый недоступный метод — запрещённый (FR-004) и не
  входящий в разрешённый перечень (FR-005) — отвергается без обращения
  к Telegram; время отказа не зависит от доступности Telegram.
- **SC-004**: Ни один вызов прокси не создаёт записей в очередях
  доставки и не порождает повторов на стороне системы; контракт
  «одно сообщение — один путь» документирован и виден потребителю.
- **SC-005**: При недоступности Telegram прокси отвечает
  распознаваемой ошибкой шлюза не дольше настроенного таймаута, не
  зависая и не блокируя параллельные запросы.

## Assumptions

- Внешний сервис-владелец ботов один на инстанс (как в 007); машинный
  ключ уже существует (фича 005), реестр ботов и сплит-хранилище
