# Research: Очередь исходящих сообщений за портом брокера

Фаза 0. Спека сознательно отложила параметры; здесь каждое решение принято
с обоснованием и альтернативами. Референс — реализация в ветке main_copy.

## RQ-1: Длительность лиза (lease)

- **Decision**: 60 секунд, настраивается (`broker_lease_seconds`,
  по умолчанию 60).
- **Rationale**: отправка в Telegram занимает <1 c в норме; 60 с — запас
  на медленный ответ и сетевые лаги, при этом зависшие строки возвращаются
  в работу через минуту, а не «зависают навсегда». В тестах значение
  уменьшается настройкой.
- **Alternatives**: 5–10 с (быстрее возврат, но ложные реклеймы при лагах
  Telegram); «вечный лиз + ручной разбор» (нарушает принцип II — надеемся
  на оператора).
- **Инвариант (I3)**: продление лиза (`renew`) в контракт v1 не входит.
  Длительность лиза обязана превышать худшее время отправки; затянувшаяся
  или зависшая отправка разрешается истечением лиза и реклеймом —
  возможен дубль, что допустимо контрактом at-least-once.

## RQ-2: Лимит попыток (max_attempts)

- **Decision**: 5 попыток, значение по умолчанию в настройках
  (`broker_max_attempts`); хранится на строке, т.к. может меняться
  настройкой между попытками.
- **Rationale**: 429 и сетевые сбои лечатся 2–3 повторами; 5 покрывает
  кластер сбоев и не даёт «отравленному» сообщению жить вечно.
- **Alternatives**: 3 (жёстче, чаще уходит в failed при серийных 429);
  10 (долго разгребается очередь у упавшего бота). Конкретное значение —
  политика воркера, контракт лишь хранит attempts/max_attempts.

## RQ-3: Задержки повторов (backoff)

- **Decision**: величину задержки передаёт вызывающий (воркер) в
  `retry(delivery, delay, reason)` — брокер лишь сохраняет
  `available_at = now() + delay`. Политика backoff (экспонента, значения
  для 429 по `retry_after`) — предмет фичи воркера, не очереди.
- **Rationale**: очередь — механизм, политика — домен воркера; contract
  не навязывает стратегию (принцип I: контракт минимальный).
- **Alternatives**: зашить экспоненциальный backoff в брокера — отвергнуто:
  адаптер RabbitMQ не смог бы единообразно его выразить.

## RQ-4: Механизм справедливости claim между ботами

- **Decision**: двухшаговый round-robin: (1) выбрать бота, дольше всех
  не получавшего захват, среди ботов с доступными строками
  (`ORDER BY COALESCE(last_claim_at, epoch)` по подмножеству bot_slug
  с доступными сообщениями); (2) взять самую старую доступную строку этого
  бота. Метка `last_claim_at` — агрегат по журналy (MAX(locked_at) по боту)
  либо отдельная маленькая таблица `bot_claim_state(bot_slug, last_claim)`,
  обновляемая в транзакции claim.
- **Rationale**: детерминированно, индексопригодно, легко тестировать;
  голодание исключено по построению (бот без захватов — первый кандидат).
- **Alternatives**: чистый FIFO (`ORDER BY available_at` глобально) —
  голодание малых ботов (отвергнуто спекой FR-004); случайный выбор бота —
  вероятностная справедливость, хуже тестируется; один SQL с window
  functions — сложнее сопровождать без выигрыша при масштабе v1.

## RQ-5: Захват строки и реклейм истёкшего лиза (PostgresBroker)

- **Decision**: одна операция `UPDATE ... WHERE id IN (SELECT ... FOR UPDATE
  SKIP LOCKED LIMIT 1) ... RETURNING` с условием выбора
  `(status='queued' AND available_at <= now()) OR (status='leased' AND
  lease_expires_at < now())` (плюс фильтр бота из RQ-4). Реклейм истёкшего
  лиза — прямой перевод в новый leased без промежуточного статуса.
- **Rationale**: SKIP LOCKED — стандарт для конкурентных очередей на
  Postgres: параллельные воркеры не блокируют друг друга; истёкший лиз
  обрабатывается тем же запросом — нет отдельного джоба «уборки».
- **Alternatives**: фоновый джоб `UPDATE leased→queued WHERE лиз истёк`
  (лишний компонент, окно между истечением и уборкой); advisory locks
  (уровень приложения, не строка).

## RQ-6: Индексы

- **Decision**:
  - частичный `messages(status, available_at) WHERE status='queued'` —
    под выбор кандидата;
  - частичный `messages(lease_expires_at) WHERE status='leased'` — под
    условие реклейма;
  - частичный `messages(bot_slug) WHERE status IN ('queued','leased')` —
    под подсчёт queue_depth.
- **Rationale**: три точечных частичных индекса меньше и точнее одного
  толстого композитного; каждый прямо соответствует одному запросу.
- **Alternatives**: единый `(status, available_at, bot_slug)` — больше
  писанины и объёма, хуже селективность.

## RQ-7: Идентификаторы

- **Decision**: `messages.id` — UUID (генерация на стороне приложения,
  uuid4), тип — PostgreSQL `UUID`.
- **Rationale**: спецификация требует UUID; клиентская генерация позволяет
  вернуть id из enqueue без round-trip (нужно фиче API).
- **Alternatives**: bigserial (меньше байт, но id предсказуемы и
  привязаны к порядку — uuid4 не даёт перебора).

## RQ-8: Раскладка контрактных тестов

- **Decision**: один сюит `tests/contract/test_broker_port.py`,
  параметризованный фикстурой `broker`: in-memory — всегда; PostgresBroker
  — `skipif(not TEST_DATABASE_URL)`. Часы: in-memory принимает инжектируемый
  clock (мгновенное истечение лиза); для Postgres-прогона тест лиза
  устанавливает `broker_lease_seconds=0.2` и ждёт ~0.3 с (единственный
  «временной» тест, допускается consciously).
- **Rationale**: эквивалентность адаптеров проверяется буквально тем же
  кодом; дублирование сюитов отвергнуто.
- **Alternatives**: два сюита (дрейф семантики), testcontainers
  (тянет Docker в dev-цикл — против конституционного «без Docker» для
  локальных прогонов; CI может добавить сервисный контейнер позже).

## RQ-9: Атомарность ack

- **Decision**: ack — одна транзакция: `UPDATE messages SET status='sent',
  telegram_message_id=:mid, sent_at=now(), lease=NULL WHERE id=:id AND
  status='leased'`. Защита от двойного ack: WHERE-условие по статусу;
  повторный ack чужой/завершённой строки — ошибка (ValueError), как
  в референсе.
- **Rationale**: конституционный инвариант (принцип II); условный UPDATE
  даёт идемпотентность по отношению к гонкам без отдельной блокировки.

## RQ-10: Настройки модуля (стандарт Configuration, C3)

- **Decision**: `src/gram_mq/settings.py` — `BaseSettings` с
  `env_prefix = "GRAMMQ_"`: `database_url: SecretStr` (required, без
  дефолта — читается как `GRAMMQ_DATABASE_URL`), `broker_lease_seconds:
  int = 60` (RQ-1), `broker_max_attempts: int = 5` (RQ-2). Env-файл —
  путь из переменной `GRAMMQ_ENV_FILE`, локальный фолбэк `./.env`;
  реальные переменные окружения приоритетнее файла (дефолт
  pydantic-settings). `SecretStr` раскрывается через
  `.get_secret_value()` ровно в одной точке — создании engine в `db.py`.
- **Rationale**: стандарт Configuration конституции: единственный канал
  настроек — GRAMMQ_-префиксные классы, секреты без дефолтов и без
  попадания в repr/логи, fail-fast при отсутствии.
- **Alternatives**: прямые `os.environ`/`os.getenv` — запрещены в
  рантайме стандартом; дефолт для database_url — секрет дефолта не имеет.
  Тесты читают `TEST_DATABASE_URL` напрямую из окружения — тесты не
  рантайм-код, граница та же, что в стандарте Asynchrony.

## RQ-11: Префикс объектов БД (GRAMMQ_TABLE_PREFIX)

- **Decision**: все таблицы, индексы, enum и констрейнты получают префикс
  из `GRAMMQ_TABLE_PREFIX` (по умолчанию `gmq`; пустая строка отключает).
  Источник — отдельный класс `TableNaming(BaseSettings)` без обязательных
  секретных полей: модели инстанцируют его на импорте, поэтому жёсткий
  `Settings.database_url` (fail-fast) не должен блокировать импорт моделей
  в окружениях без БД (юнит-тесты, alembic offline). Миграция 0001 и
  TRUNCATE в conftest строят имена тем же хелпером `table_name()`.
- **Rationale**: неймспейсинг в разделяемой БД (несколько приложений в одной
  базе) без изменения кода; префикс фиксирован при накате первой миграции —
  переименование на живой базе не поддерживается (alembic не отслеживает
  переименования, история ревизий бы разошлась).
- **Alternatives**: PostgreSQL-схемы (`search_path`) — идиоматичнее, но
  меняют строку подключения и права; хардкод имён — нет гибкости;
  переименование через миграцию — отвергнуто сознательно (фиксация при
  рождении базы).
