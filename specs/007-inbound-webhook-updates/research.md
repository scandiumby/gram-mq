# Research: Приём вебхуков Telegram и доставка апдейтов внешнему сервису

**Date**: 2026-11-21 | **Spec**: [spec.md](spec.md) | **Plan**: [plan.md](plan.md)

Фаза 0. Решения приняты по конституции v3.0.0 (+ операторские ограничения
сессии 2026-11-21 (2)), кодовой базе (ports, adapters, миграции 0001–0003,
`worker/runner.py`, `token_store.py`, CLI) и FR-001–FR-011 спеки.
NEEDS CLARIFICATION в спеке нет — все развилки сведены здесь в решения с
отвергнутыми альтернативами.

## R1. Поверхность вебхука: путь и идентификация бота

**Decision**: пер-ботовый маршрут `POST /webhooks/{bot_slug}`; бот
определяется slug'ом из пути, аутентификация — заголовком
`X-Telegram-Bot-Api-Secret-Token` (стандартный механизм Telegram
`set_webhook(secret_token=…)`), сверка — по строке реестра бота.

**Rationale**: Telegram позволяет один вебхук на токен бота; slug в пути
даёт публичный, человекочитаемый адрес (единый идентификатор бота по
конституции Stack v1) и логи без раскрытия секрета. Секрет в заголовке, а
не в пути: путь попадает в логи прокси/сервера, заголовок — нет; это же
механизм, который Telegram документировал именно против подделки
вебхуков.

**Alternatives**: (а) единый `/webhook` с определением бота по секрету —
деградирует в перебор всех HMAC на каждый запрос и лишает адрес
читаемости; (б) `/webhooks/{secret}` (недоказуемый URL) — секрет в логах
прокси, смена секрета = смена адреса, телеметрия бесполезна; (в) webhook
через Bot API long polling вместо вебхуков — прямо исключено спекой
(FR-001: эндпоинт приёма) и требует постоянного соединения с Telegram на
каждый бот.

## R2. Хранение и проверка секрета вебхука

**Decision**: в момент `webhook set` система генерирует секрет
`secrets.token_urlsafe(32)` (алфавит `[A-Za-z0-9_-]` — разрешённый
Telegram'ом charset `secret_token`, 43 символа ≤ 256), один раз передаёт
его в `set_webhook` и пишет в `gmq_bots.webhook_secret_hmac` значение
`hmac_sha256(GRAMMQ_WEBHOOK_MASTER_KEY, secret).hexdigest()` — String(64).
Проверка запроса: `hmac.compare_digest(hmac(key, presented).hexdigest(),
stored_hex)`. NULL колонки = приём выключен. Мастер-ключ — отдельный
`GRAMMQ_WEBHOOK_MASTER_KEY` (hex 32 байта, SecretStr, без дефолта);
отсутствует → CLI `webhook set` отказывает (exit 2), эндпоинт для ботов
без значения отвечает 404.

**Rationale**: секрет — предъявляемый многократно bearer-креденшл на
горячем пути (сотни хитов/мин), Argon2id (~десятки мс CPU на хит) взял бы
большую часть бюджета SC-002 (≤ 1 c) и стал бы CPU-DoS-вектором на
открытом эндпоинте. Конституция III для этого класса креденшлов
предписывает HMAC-SHA256 («OTP and refresh tokens as HMAC-SHA256»):
микросекунды, constant-time сверка дайджестов, plaintext для проверки не
нужен (FR-008). Выделенный мастер-ключ — «shared by no other purpose»:
утечка одного ключа не компрометирует токены ботов, и наоборот. Потеря
ключа = все вебхуки 401 до перерегистрации — тот же recovery-контракт,
что у токенов 006 («re-issuing»).

**Alternatives**: (а) Argon2id-хэш как у API-ключей — горячесть пути
запрещает (см. выше); API-ключи проверяются на два порядка реже;
(б) голый SHA-256 дайджест без ключа — криптографически терпимо (секрет
256-битный случайный), но отходит от буквы конституции III и даёт
атакующему с дампом БД офлайн-оракул для перебора *проверочных*
значений; (в) AESGCM-шифрование секрета с расшифровкой на каждый запрос
— расшифрованный plaintext лишний раз в памяти и тот же ключ, больше
кода без выигрыша; (г) переиспользовать `GRAMMQ_TOKEN_MASTER_KEY` —
прямо запрещено конституцией (dedication).

## R3. Очередь входящих: сиблинг-порт, а не обобщение BrokerPort

**Decision**: новый доменный порт `InboundBrokerPort`
(`enqueue_inbound` / `claim` / `ack` / `retry` / `dead_letter` /
`queue_depth`) в `ports/inbound.py` с собственными датаклассами
`InboundUpdate(id, bot_slug, update_id, payload)` и `InboundDelivery` —
семантика зеркальна `BrokerPort`, типы — входящие; ошибки
`UnknownBotError`/`IllegalDeliveryStateError` переиспользуются из
`ports/broker.py`.

**Rationale**: контракт `BrokerPort` исходящий насквозь:
`OutboundMessage.chat_id`, `Delivery.telegram_message_id` в ack — входящий
поток протаскивал бы бессмысленные поля или пустые строки. Конституция I
говорит о новых членах порта под нужду адаптера; здесь нужда — целое
новое направление потока, и у него своя таблица-журнал. Контрактные тесты
нового порта пишутся по образцу `tests/contract/test_broker_port.py`.

**Alternatives**: (а) обобщить `BrokerPort` до генерика `QueuePort[T]` —
переписывание проверенного контракта фичи 001 и обоих адаптеров ради
изоморфных типов; риск регрессии неокупаем; (б) та же таблица
`gmq_messages` с колонкой `direction` — разные полезные поля
(`update_id` vs `chat_id`+`telegram_message_id`), разные терминальные
статусы (`delivered` vs `sent`), индексы под оба потока сразу; журнал
смешивает несмешиваемое; (в) RabbitMQ для входящих — новый брокер при
живом Postgres-подходе «очередь = журнал» (Stack v1), нарушение
минимальности.

## R4. Схема: журнал входящих, ledger справедливости, колонка реестра

**Decision**: миграция `0004` (через `table_name()`, т.е. с
`GRAMMQ_TABLE_PREFIX`): таблица `gmq_inbound_updates` — зеркало
`gmq_messages` по lease-механике, но: `update_id BigInteger NOT NULL`
вместо `chat_id`, свой статус-enum `gmq_inbound_status`
(`queued/delivering/delivered/failed`), `delivered_at` вместо
`sent_at`, без `telegram_message_id`; партициальные индексы
claim/reclaim/depth + НЕуникальный индекс `(bot_slug, update_id)` —
эксплуатация повторов и опора мягкого дедупа (R13). Отдельная таблица `gmq_bot_inbound_claim_state`
(bot_slug PK, last_claim_at) — round-robin справедливость входящей
очереди. `ALTER TABLE gmq_bots ADD COLUMN webhook_secret_hmac
String(64) NULL`. Без FK на `gmq_bots` — журнал переживает ревок бота
(решение миграции 0003 для исходящих, распространено на входящие).

**Rationale**: статусы названы языком спеки (`delivering` = leased-состояние
воркера, US4); неуникальный `(bot_slug, update_id)` — материальный
документированный допуск дублей at-least-once (SC-005): UNIQUE превратил
бы контракт в exactly-once и молча резал бы честные повторы Telegram.
Отдельный claim-ledger: одна таблица на два потока заставила бы очереди
бороться за `last_claim_at` одного бота и ломала бы справедливость.
Колонка в `gmq_bots`, а не отдельная таблица: ревок бота гасит приём
автоматически (строка умирает вместе с секретом), нет сиротской таблицы.

**Alternatives**: (а) `webhook_secrets` отдельной таблицей с FK —
orphan-строки после ревока или каскады против «журнал переживает бота»;
(б) статус-enum исходящих + поле `sent_at` — ложная семантика «отправлено
в Telegram» для доставленного наружу; (в) `update_id` как String —
сортировка/сравнение по числу теряется, Telegram гарантирует int.

## R5. Доставка наружу: таксономия ошибок и экспоненциальный backoff

**Decision**: порт `UpdateDeliverer.deliver_update(update: dict) -> None`
с исключением `DeliveryError(reason, *, retry_after=None, permanent=False)`
— зеркало `TelegramSender`/`TelegramSendError`. Разделение решений:
таймаут/обрыв/5xx → `broker.retry(delay = min(base * 2**attempts, 300s))`
со счётом попытки; 429 → retry на `retry_after` БЕЗ счёта попытки (ждать
окно лимита — не неудачная попытка апдейта); остальные 4xx → сразу
`dead_letter` (эндпоинт отверг апдейт, повтор бессмыслен, FR-006);
исчерпание `max_attempts` → `failed`. Формула и cap 300 c — те же, что в
`worker/runner.py` (BACKOFF_CAP_SECONDS).

**Rationale**: операторское ограничение «экспоненциально нарастающая
задержка без лишней нагрузки» (сессия (2)) совпадает с уже проверенной
политикой исходящих — единая механика, нулевая новая материя. Немонотонный
429-потолок (Retry-After может быть меньше текущего backoff) учтён
приоритетом `retry_after`.

**Alternatives**: (а) линейный/фиксированный retry — нарушает ограничение
оператора и нагрузит лежащий сервер; (б) повторять и 4xx — жечь попытки
на безнадёжных (404/410 эндпоинта), против FR-006; (в) джиттер —
полезен при десятках параллельных воркеров, у нас один inbound-worker на
инстанс; не добавляем (заметка на будущее при масштабировании).

## R6. HTTP-клиент доставки: httpx

**Decision**: `httpx.AsyncClient` — постоянный клиент в процессе
inbound-worker, POST JSON, таймаут из `GRAMMQ_INBOUND_DELIVERY_TIMEOUT_SECONDS`
(дефолт 10 c), опциональный заголовок авторизации
(`inbound_delivery_auth_header_name` / `_value`). httpx переезжает из
dev-зависимостей (уже используется в тестах через ASGITransport) в
runtime. Классификация ответа — чистой функцией `classify()`, тестируемой
без сети (по образцу `classify` в aiogram-адаптере).

**Rationale**: async+typed (mypy --strict), уже в дереве зависимостей
проекта (тесты), BSD-3-Clause. Тело — исходный `dict` payload; httpx
сериализует JSON — побитовая идентичность не гарантируется на уровне
байтов строки, гарантируется семантическая: тот же JSON-объект без
трансформации полей (SC-003 читается как «payload без модификации»).

**Alternatives**: (а) aiohttp напрямую — уже транзитивно через aiogram,
но объявлять прямую зависимость от транзитной — хрупко; (б) re-use
aiogram-машинерии — она про Telegram Bot API, не про произвольный POST;
(в) `urllib`/`requests` — запрещены конституцией (Asynchrony).

## R7. CLI `gram-mq webhook set|delete`: порядок операций

**Decision**: `webhook set <bot_slug>`: (1) собрать токен бота обеими
половинами через существующий `SplitFileBotConfig` (NotRegistered /
NotReady / нет `webhook_public_url` / нет `webhook_master_key` → exit 2);
(2) сгенерировать секрет; (3) `aiogram Bot.set_webhook(url=f"{public}/
webhooks/{slug}", secret_token=secret)` — сетевой вызов Telegram; успех →
(4) записать HMAC в строку бота (exit 4 при сбое записи). `webhook delete
<bot_slug>`: deleteWebhook → `webhook_secret_hmac = NULL`. Порядок
«Telegram первым, БД второй»: в БД значение появляется только когда
Telegram его уже знает; сбой посередине оставляет Telegram при старом
секрете → эндпоинт 401 до перезапуска команды (безопасное направление:
артефактов нет, потерь нет), повтор команды идемпотентен (новый секрет,
новый set_webhook, перезапись колонки).

**Rationale**: зеркалит оконную дисциплину 005/006 — система действует от
имени уже известного секрета, plaintext живёт только в памяти CLI в окно
операции (конституция III). Exit-коды — действующая конвенция CLI (0/2/4).

**Alternatives**: (а) БД первой — риск: записан секрет, Telegram не
принял → приём 401 при «успешной» команде; то же количество перезапусков,
хуже семантика; (б) HTTP-эндпоинт управления вебхуком вместо CLI — ещё
один оконный surface без нужды: у CLI уже есть доступ к половинам токена,
эндпоинт пришлось бы снабжать каналом передачи секрета; спека выбрала CLI
(US3); (в) авто-регистрация при создании бота — слияет фичи 006 и 007,
публичный адрес известен не всегда, спека разделяет.

## R8. Эндпоинт приёма: коды ответа и валидация тела

**Decision**: `POST /webhooks/{bot_slug}`, тело — произвольный JSON-объект
апдейта; обязательное поле — `update_id: int` (отсутствие/не-int → 422,
артефактов нет). Коды: 200 — после COMMIT очереди; 401 — заголовок
отсутствует/не совпал (единый ответ, без различения причин); 404 — бот не
зарегистрирован ИЛИ приём выключен (NULL-секрет: неотличимо от
неизвестного бота, без оракула); 503 — сбой фиксации (Telegram повторит);
422 — некорректное тело. Регистрация маршрута — только при инъекции портов
(иначе 404 на всём `/webhooks/*`, обратная совместимость тестов/деплоев).
Payload не логируется (только id/bot/update_id).

**Rationale**: Telegram различает только 2xx/не-2xx и повторяет при
неудаче — это и есть отказоустойчивость FR-002/US1-сценарий 4.
`update_id` — единственное поле, которое система обязана понять (журнал,
FR-010, дедуп потребителем); всё остальное — тёмный груз (FR-008: без
интерпретации). 404-неотличимость выключенного приёма — не оракул
состояния ботов.

**Alternatives**: (а) pydantic-схема всех полей апдейта — привязка к
эволюции Bot API, против «все типы апдейтов как есть»; (б) 403 для
выключенного приёма — оракул существования бота; (в) 500 на сбой БД —
Telegram повторяет и на 5xx, но 503 точнее семантически.

## R9. Синхронная часть хендлера: бюджет немедленного 200

**Decision**: в запросе выполняется ровно: SELECT строки бота (+HMAC),
constant-time сверка, INSERT журнала, COMMIT, 200. Ни доставки, ни
воркера, ни логирования payload, ни Argon2 (R2). Сбой на INSERT/COMMIT →
503 без артефактов (транзакция абортирована).

**Rationale**: операторское ограничение «немедленный 200 критичен» +
SC-002 ≤ 1 c: два сетевых round-trip к БД и микросекунды CPU — единицы
мс. Готовность внешнего сервера не входит в путь в принципе (US1-сценарий
5).

**Alternatives**: (а) фиксация в фоне после 200 (fire-and-forget task) —
краш до фиксации теряет подтверждённый Telegram'у апдейт, прямое
нарушение конституции II; (б) буфер в памяти процесса с батч-коммитом —
то же окно потери; отвергнуто.

## R10. Настройки: перечень и дефолты

**Decision**: `webhook_public_url: str | None = None`;
`webhook_master_key: SecretStr | None = None`;
`inbound_delivery_url: str | None = None`;
`inbound_delivery_auth_header_name: str = "Authorization"`;
`inbound_delivery_auth_header_value: SecretStr | None = None`;
`inbound_delivery_timeout_seconds: float = 10.0`. Poll/backoff/lease/
max_attempts — общие с исходящими (`worker_poll_interval`,
`worker_backoff_base_seconds`, `broker_lease_seconds`,
`broker_max_attempts`). `.env.example` расширяется с окнами применения.

**Rationale**: дефолты верны во всех окружениях (None = фича не
используется) — конституция Configuration; секреты — SecretStr; единый
env-файл на все процессы. Общие тюннинги воркеров: один оператор, один
деплой, отдельные ручки не несут разницы среды.

**Alternatives**: отдельные `inbound_worker_*` ручки — конфигурационный
раздув без сценария различия; отвергнуто (добавятся при реальной нужде).

## R11. Третий процесс и деплой

**Decision**: пакет `src/gram_mq/inbound_worker/` + консольный скрипт
`gram-mq-inbound-worker`; сборка в `main.py` с fail-fast: нет
`GRAMMQ_INBOUND_DELIVERY_URL`/`DATABASE_URL` — процесс падает на старте с
ясной ошибкой. `deploy/run_all.py`: третий сервис порождается только при
наличии `GRAMMQ_INBOUND_DELIVERY_URL` в окружении (deploy-артефакт читает
указатель-переменную, не секрет). systemd: новый юнит
`gram-mq-inbound-worker.service` (близнец worker-юнита). Dockerfile/CMD
не меняются (run_all уже стартовый).

**Rationale**: спека требует отдельный воркер (US2); условный старт
сохраняет один образ/юнит-набор для исходящих деплоев без лишнего
падающего процесса. run_all — не runtime-код (конституция Asynchrony/
Configuration допускают), читает только наличие переменной.

**Alternatives**: (а) второй loop в существующем `gram-mq-worker` —
нарушение US2 (спека: «другой воркер»), падение доставки кладёт исходящие
и наоборот; (б) безусловный третий процесс — crash-loop на исходящих
деплоях; (в) флаг `GRAMMQ_INBOUND_ENABLED` — ещё одна ручка поверх уже
несущей смысл переменной delivery_url.

## R12. Ограничения Telegram, учтённые дизайном

**Decision**: принять как внешние: вебхук требует публичный HTTPS-адрес
(порты 443/80/88/8443) — поэтому `webhook_public_url` обязателен для CLI,
TLS терминируется инфраструктурой (Assumptions спеки); `secret_token`
charset `[A-Za-z0-9 _-]`, 1–256 — `token_urlsafe(32)` попадает;
`set_webhook` без `allowed_updates` оставляет дефолтный набор Telegram
(все обычные типы) — не задаём, проходить должно всё; `drop_pending_updates`
не задаём (дефолт False — не терять); `max_connections` — дефолт 40.
Медленный ответ (несколько секунд) Telegram считает неудачей и повторяет
апдейт — покрыто R9 и edge-кейсом спеки о дублях.

**Rationale**: всё перечисленное — внешний контракт Bot API; система
проектируется под его границы, не преодолевая их.

**Alternatives**: явный `allowed_updates` со списком — фиксация набора,
противоречащая «все типы апдейтов без фильтрации» (Future Enhancements —
фильтрация, тогда и появится).

## R13. Ингест-дедуп ретраев Telegram: мягкий, со сверкой payload

**Decision** (сессия 2026-11-21 (3), оператор после разбора вариантов):
`enqueue_inbound` идемпотентен по ключу (bot_slug, update_id, payload):
перед вставкой — единый SELECT (существование бота + наличие точно такой
же записи; JSONB-равенство payload, поиск по индексу (bot_slug,
update_id)). Точное совпадение — поглощение без артефакта, эндпоинт
отвечает 200; то же update_id с иным содержимым — новая запись. Никакого
UNIQUE-ограничения: гонка конкурентных вставок может просачить дубль —
безвредно, дубли доставки и так контрактны.

**Rationale**: настоящий ретрай Telegram байт-в-байт идентичен
(поглощается), а update_id Telegram переиспользует после ≥ недели
простоя бота (случайная новая база) — жёсткий UNIQUE молча терял бы
такой новый апдейт, ослабляя SC-001; сверка payload различает эти
случаи. Ретраи одного апдейта идут от Telegram последовательно (повтор
стартует после таймаута предыдущей попытки — вставка давно
закоммичена), поэтому SELECT-проверка ловит практически все реальные
дубли. Цена — расширение уже существующего SELECT бота: hot path не
удлиняется. Контракт приёмника дополнен: дедуп скользящим окном по
(бот, update_id), не вечным множеством.

**Alternatives**: (а) UNIQUE + ON CONFLICT DO NOTHING — канал тихой
потери при коллизии после простоя (отвергнут оператором после разбора);
(б) без дедупа вовсе (решение сессии 1) — допустимо, но ретраи после
потерянных ответов систематически шумят очередью и доставкой;
(в) дедуп с TTL-окном (считать совпадение только в пределах N часов) —
усложнение: payload-сверка уже даёт нужную дискриминацию.
