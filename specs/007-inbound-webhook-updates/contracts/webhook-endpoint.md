# Contract: Эндпоинт приёма вебхуков

**Spec**: FR-001, FR-002, FR-008, FR-009; US1 | **Research**: R1, R8, R9

Третье URL-пространство (не `/api/v1/*`, не `/api/dashboard/*`, не
`/bootstrap/*`). Вызывающий — Telegram Bot API (delivery of updates);
маршрут регистрируется в приложении только при инъекции портов
`InboundBrokerPort` + `WebhookAuth` (иначе весь `/webhooks/*` — 404).

## Запрос

```text
POST /webhooks/{bot_slug}
X-Telegram-Bot-Api-Secret-Token: <секрет вебхука бота>
Content-Type: application/json

<произвольный JSON-объект апдейта Telegram>
```

- `bot_slug` — slug зарегистрированного бота (реестр — источник истины);
- заголовок секретa обязателен; сверка — constant-time по HMAC-дайджестам
  (см. [webhook-admin-cli.md](webhook-admin-cli.md));
- тело не разбирается по схеме: обязательное поле — только `update_id: int`
  (отсутствие / не int → 422, артефактов нет); всё остальное — тёмный груз.

## Ответы

| Код | Условие | Артефакты |
|---|---|---|
| 200 | строка журнала зафиксирована (COMMIT) ИЛИ ретрай поглощён мягким дедупом (совпадение bot_slug + update_id + payload) | новая запись `queued`, либо ничего (поглощение ретрая) |
| 401 | заголовок отсутствует или не совпал | нет |
| 404 | бот не зарегистрирован ИЛИ приём выключен (webhook_secret_hmac IS NULL) — неразличимо | нет |
| 422 | тело не JSON-объект или нет корректного `update_id` | нет |
| 503 | сбой фиксации (хранилище) | нет (транзакция абортирована) |

401 — единый ответ без различения «нет заголовка»/«не тот секрет», без
эха секрета. 404-неотличимость выключенного приёма — без оракула
состояния ботов.

## Тайминг (операторское ограничение «немедленный 200»)

Синхронная часть запроса — только: SELECT строки бота (+HMAC), сверка,
INSERT журнала, COMMIT. Ни доставки, ни воркера, ни логирования payload.
Бюджет SC-002: ≤ 1 c при исправном хранилище (фактически — единицы мс:
два round-trip к БД и микросекунды HMAC). Telegram считает медленный/не-2xx
ответ неудачей доставки и присылает апдейт заново — поэтому 200 выдаётся
строго после COMMIT, а сбой фиксации отвечает 503 (Telegram повторит).

## Дубликаты: мягкий дедуп на входе, at-least-once на доставке

- Ретрай Telegram того же апдейта (байт-в-байт тот же JSON) — поглощается
  на входе: совпадение (bot_slug, update_id, payload) не создаёт записи,
  200 возвращается всё равно — Telegram добился своего, апдейт надёжно
  зафиксирован (FR-012).
- То же update_id с другим содержимым — новый апдейт (Telegram после ≥
  недели простоя бота выбирает update_id заново): принимается и
  доставляется. UNIQUE-ограничения на (bot_slug, update_id) нет
  намеренно — оно молча теряло бы такие апдейты.
- Гонка конкурентных вставок одного ретрая и реклейм lease упавшего
  воркера (краш между успешным POST и ack) могут дать дубль ДОСТАВКИ —
  неустранимое окно at-least-once (SC-005); приёмник дедуплицируется
  скользящим окном по (bot_slug, update_id), не вечным множеством.
