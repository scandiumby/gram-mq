# Feature Specification: Приём вебхуков Telegram и доставка апдейтов внешнему сервису

**Feature Branch**: `007-inbound-webhook-updates`

**Created**: 2026-11-21

**Status**: Draft

**Input**: User description: "Концепция дополняется: теперь нужно не только отправлять сообщения в телеграм, но и ловить входящие обновления через вебхуки ботов, ставить их также в очередь, и другой воркер должен отправлять их на внешний сервер на эндпоинт для обновления бота"

## Clarifications

### Session 2026-11-21 - MVP-дефолты (автономно, по умолчанию)

Дефолты приняты без вопроса оператору и revisitable: любое изменение —
правкой этой сессии до plan.

- Q: Один целевой эндпоинт доставки на систему или на каждого бота?
  → A: в MVP — один системный целевой эндпоинт (внешний
  сервис-владелец ботов один, его эндпоинт обновлений задаётся в
  конфигурации инстанса); маршрутизация апдейтов разных ботов по разным
  эндпоинтам — Future Enhancements.
- Q: Нужна ли авторизация при доставке на внешний сервер? → A:
  опциональный auth-заголовок из конфигурации: задан — добавляется к
  каждому запросу доставки, не задан — запросы уходят без него.
- Q: Какие апдейты пересылать внешнему серверу? → A: все и без
  изменений: payload апдейта передаётся как есть, без интерпретации и
  фильтрации типов (сообщения, callback-и, редактирования и т.д.);
  фильтрация — Future Enhancements.
- Q: Дедупликация по update_id на стороне системы? → A: нет — контракт
  доставки at-least-once (конституция II), редкий дубль возможен и
  документирован; потребитель дедуплицируется парой (бот, update_id).
- Q: Что делать с ошибками внешнего сервера? → A: таймаут, обрыв
  соединения, 429 и 5xx — повтор с нарастающей задержкой; остальные 4xx —
  сразу failed без повторов (эндпоинт отверг апдейт, повтор бессмыслен).
- Q: Как аутентифицируется приём вебхука? → A: секретом вебхука,
  который система генерирует сама и один раз передаёт Telegram'у при
  регистрации вебхука; оператор его не видит и не вводит; для проверки
  входящих запросов достаточно проверочного значения, открытый текст
  секрета в системе не хранится.
- Q: Кто регистрирует вебхук у Telegram? → A: CLI системы —
  санкционированный путь (по аналогии с выдачей ключей и регистрацией
  бота); CLI также снимает вебхук для остановки приёма.

### Session 2026-11-21 (2) - Ограничения оператора (обязательны для плана)

Даны оператором явно; дополняют и уточняют дефолты первой сессии.

- Секрет вебхука (WEBHOOK_SECRET) един и в регистрации set_webhook, и в
  проверке входящих: Telegram присылает его в заголовке
  `X-Telegram-Bot-Api-Secret-Token`; эндпоинт отклоняет запросы без
  заголовка и с неверным значением.
- Немедленный успех (200 OK) критичен: Telegram ждёт ответа вебхука и
  при медленном ответе считает доставку неуспешной и присылает апдейт
  заново → постановка в очередь — единственная синхронная работа
  эндпоинта, пересылка внешнему серверу — только в фоне.
- Очередь переживает перезапуски стабильного сервера (самой системы);
  пока нестабильный внешний сервер недоступен, апдейты не теряются, а
  ждут в таблице очереди.
- Повторы доставки — с экспоненциально нарастающей задержкой, чтобы
  временно недоступный внешний сервер не получал лишней нагрузки.

### Session 2026-11-21 (3) - Внешние рекомендации: принятые решения

Архитектурные рекомендации (входящий шлюз + исходящий прокси) сверены со
спекой и конституцией; где то же самое называется иначе — остаются
проектные имена.

- Q: Терминология рекомендаций? → A: соответствие закреплено:
  pending/processing/done/failed = наши queued/delivering/delivered/
  failed; next_attempt_at = available_at; единый /telegram/webhook =
  наш пер-ботовый /webhooks/{bot_slug} (система мультисботовая);
  отказ 403 при неверном секрете = наш недифференцированный 401;
  retry 1-2-4-8…60 c = наш экспоненциальный backoff с настройками
  (база 5 c, кап 300 c, max_attempts 20 — всё через GRAMMQ_-переменные).
- Q: Дедупликация по update_id при записи (обновляет решение сессии 1)?
  → A: мягкий дедуп по ключу (бот, update_id, payload): настоящий
  ретрай Telegram (байт-в-байт тот же апдейт) поглощается на входе без
  артефактов, Telegram'у всё равно возвращается успех; то же update_id с
  другим содержимым (случайная коллизия после ≥ недели простоя бота —
  Telegram выбирает update_id заново) принимается как новый апдейт.
  Ограничения уникальности в схеме нет: гонка конкурентных вставок может
  просачивать дубль — безвредно. Дубли доставки остаются ровно в
  неустранимом случае — крах воркера между успешным POST и ack (окно
  закрывается lease-реклеймом, повторная доставка возможна).
- Q: Контракт приёмной стороны (нестабильного сервера)? → A:
  документируется как обязательный контракт потребителя: успех — только
  после успешной обработки апдейта; дедуп — скользящим окном по
  (бот, update_id), не вечным множеством (update_id переиспользуется
  Telegram после недели простоя); таймаут доставки настраивается с
  запасом на худшее время обработки приёмником.
- Q: Исходящий прокси /api/{method} из рекомендаций? → A: смежная
  отдельная фича 008 (токен не покидает стабильный сервер; очередь
  исходящих — основной путь, прокси — для вызовов, где боту нужен
  результат сразу; правило «не дублировать один вызов в очередь и
  прокси» уйдёт в спеку 008). Спека 007 остаётся входящим потоком.
- Q: Мониторинг очереди из рекомендаций? → A: без новых эндпоинтов: к
  журналу (US4) добавляется возраст старейшей незавершённой записи —
  индикатор «нестабильный сервер лежит дольше, чем готовы ждать»;
  глубина очереди и число failed уже покрываются журналом.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Приём апдейта от Telegram без потерь (Priority: P1)

Как бот в Telegram, я присылаю свои обновления на вебхук-эндпоинт
системы; она проверяет секрет вебхука, проверяет бота по реестру и
долговременно фиксирует апдейт в очереди входящих, и только после
фиксации отвечает Telegram'у успехом. Приём никогда не ждёт ни доставки
внешнему серверу, ни его доступности.

**Why this priority**: это единственная точка входа апдейтов в систему;
без неё нет предмета доставки, и потеря здесь невосполнима (Telegram
повторяет только пока получает отказ).

**Independent Test**: отправить на вебхук апдейт с корректным секретом
(успешный ответ, в журнале входящих появилась запись queued, переживающая
перезапуск процессов); повторить с неверным секретом и для
незарегистрированного бота (отказ, артефактов нет).

**Acceptance Scenarios**:

1. **Given** зарегистрированный бот с активным вебхуком и секретом S,
   **When** Telegram присылает апдейт с корректным секретом, **Then**
   система немедленно отвечает успехом, и апдейт зафиксирован в журнале
   входящих со статусом queued; запись переживает перезапуск любого
   процесса.
2. **Given** запрос на вебхук без заголовка секрета или с неверным
   значением, **When** система проверяет его, **Then** запрос
   отклоняется, и в журнале не появляется никаких артефактов.
3. **Given** апдейт для бота, отсутствующего в реестре, **When** он
   приходит на вебхук, **Then** следует отказ «бот не найден», артефактов
   не создаётся.
4. **Given** очередь недоступна для фиксации (сбой хранилища), **When**
   Telegram присылает апдейт, **Then** система отвечает ошибкой (не
   успехом), так что Telegram повторяет отправку — апдейт не потерян.
5. **Given** внешний сервер лежит, **When** Telegram присылает апдейты,
   **Then** приём продолжает отвечать успехом: время ответа вебхука не
   зависит от внешнего сервера.
6. **Given** в журнале уже есть запись (бот, update_id, payload),
   **When** Telegram повторно присылает байт-в-байт тот же апдейт,
   **Then** система отвечает успехом без новой записи (поглощение
   ретрая); апдейт с тем же update_id, но другим содержимым принимается
   как новый.

### User Story 2 - Доставка апдейтов внешнему сервису (Priority: P1)

Как внешний сервис-владелец ботов, я получаю все апдейты моих ботов на
свой эндпоинт обновлений: отдельный воркер входящих забирает их из
очереди и доставляет payload без изменений, фиксируя доставку атомарно.
Если мой эндпоинт недоступен — апдейты копятся в очереди и доставляются
после восстановления; если эндпоинт отвергает апдейт — он виден в
журнале как failed.

**Why this priority**: это ценность фичи для внешнего сервиса —
гарантированная доставка того, что бот принял; вместе со story 1 образует
сквозной поток «ни один апдейт не потерян».

**Independent Test**: положить в очередь входящих апдейт вручную и
убедиться, что воркер доставил его на тестовый эндпоинт без изменений и
зафиксировал delivered; уронить эндпоинт и увидеть повторы с нарастающей
задержкой и переход в failed после исчерпания попыток.

**Acceptance Scenarios**:

1. **Given** апдейт в статусе queued и доступный внешний эндпоинт,
   **When** воркер входящих его обрабатывает, **Then** payload доставлен
   без изменений, и в журнале атомарно зафиксирован статус delivered.
2. **Given** внешний эндпоинт недоступен (таймаут, обрыв, 429, 5xx),
   **When** воркер пытается доставить, **Then** апдейт остаётся в
   очереди, попытки повторяются с экспоненциально нарастающей
   задержкой; после исчерпания максимума попыток — статус failed.
3. **Given** внешний эндпоинт ответил необратимым отказом (4xx, кроме
   429), **When** воркер получает ответ, **Then** апдейт сразу переводится
   в failed без повторов.
4. **Given** апдейт доставляется и процесс воркера обрушивается между
   отправкой и фиксацией, **Then** апдейт не теряется: после истечения
   lease он забирается снова — возможен редкий дубль доставки
   (at-least-once, документированный контракт).

---

### User Story 3 - Регистрация вебхука бота (Priority: P2)

Как оператор на сервере, я запускаю CLI-команду регистрации вебхука для
зарегистрированного бота: система сама генерирует секрет, сообщает
Telegram'у адрес вебхука и секрет и включает приём апдейтов этого бота.
Обратная команда снимает вебхук и останавливает приём.

**Why this priority**: без регистрации Telegram не знает, куда слать
апдейты; но это разовое административное действие, а не поток, поэтому
P2, а не P1.

**Independent Test**: выполнить регистрацию для бота и убедиться, что
Telegram подтверждает активный вебхук; после снятия — что Telegram
подтверждает отсутствие вебхука, а входящие запросы с прежним секретом
отклоняются.

**Acceptance Scenarios**:

1. **Given** зарегистрированный бот и публичный адрес системы, **When**
   оператор выполняет CLI-команду регистрации вебхука, **Then** у
   Telegram выставлен вебхук, секрет сгенерирован системой и передан
   Telegram'у, а оператор нигде не видит секрет в открытом виде.
2. **Given** бот с активным вебхуком, **When** оператор выполняет
   CLI-команду снятия вебхука, **Then** Telegram больше не шлёт апдейты,
   а прямые запросы на эндпоинт этого бота отклоняются.

---

### User Story 4 - Наблюдаемость потока входящих (Priority: P3)

Как оператор, я средствами журнала (как для исходящих) вижу состояние
потока входящих: глубину очереди, количество доставленных и упавших
апдейтов, число попыток и последнюю ошибку каждого failed-апдейта.

**Why this priority**: эксплуатация без статистики возможна (журнал
есть), но поиск причин сбоев внешнего сервера без неё дорог; отдельные
эндпоинты статистики и дашборд — вне MVP.

**Independent Test**: создать апдейты в разных состояниях (queued,
delivered, failed) и получить по журналу их количества и детали
последнего failed-апдейта.

**Acceptance Scenarios**:

1. **Given** апдейты в состояниях queued/delivered/failed, **When**
   оператор запрашивает журнал, **Then** он видит количество по каждому
   состоянию, глубину очереди и возраст старейшей незавершённой записи —
   индикатор «внешний сервер недоступен дольше, чем готовы ждать».
2. **Given** failed-апдейт, **When** оператор смотрит его запись,
   **Then** видит число попыток и последнюю ошибку доставки.

### Edge Cases

- Telegram повторяет один и тот же апдейт (система ответила ошибкой или
  не успела ответить вовремя — медленный ответ Telegram считает
  неуспешной доставкой и присылает заново) → байт-в-байт тот же апдейт
  поглощается мягким дедупом на входе; просачивание возможно только при
  гонке конкурентных вставок → тогда внешний сервер может получить
  дубль: допустимо по контракту at-least-once.
- update_id совпал со старой записью при другом содержимом (Telegram
  после ≥ недели простоя бота выбирает update_id заново случайно) →
  принимается как новый апдейт и доставляется; отсюда требование к
  приёмнику: дедуп скользящим окном, а не вечным множеством update_id.
- Тело запроса вебхука не соответствует формату апдейтов → отказ с
  ошибкой запроса, артефактов не создаётся.
- Внешний сервер отвечает медленно → запрос доставки обрывается по
  таймауту, считается сетевым сбоем, апдейт уходит на повтор.
- Внешний сервер лежит продолжительное время, апдейты продолжают
  поступать → очередь растёт и ждёт в таблице (не теряясь при
  перезапусках самой системы), приём не блокируется и не деградирует.
- Бот удалён из реестра, а его апдейты ещё в очереди → они доставляются
  как обычно (журнал — источник истины); новые запросы вебхука этого
  бота отклоняются.
- Секрет вебхука скомпрометирован → перегенерация секрета повторной
  регистрацией вебхука; старый секрет перестаёт приниматься.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Система MUST предоставлять эндпоинт приёма вебхуков для
  апдейтов Telegram-ботов, отдельный от пространства URL машинного
  (`/api/v1/*`) и человеческого (`/api/dashboard/*`) доступов, с
  собственной аутентификацией по секрету вебхука, который Telegram
  передаёт в заголовке `X-Telegram-Bot-Api-Secret-Token`.
- **FR-002**: Система MUST отвечать Telegram'у немедленным успехом сразу
  после долговременной фиксации апдейта в очереди входящих — фиксация в
  очереди остаётся единственной синхронной работой эндпоинта; при
  невозможности фиксации — отвечать ошибкой, чтобы Telegram повторил
  отправку.
- **FR-003**: Система MUST ставить входящие апдейты в очередь через
  брокер с теми же гарантиями, что исходящие сообщения: lease на
  обработку, счётчик попыток, повторы с экспоненциально нарастающей
  задержкой, статус failed после исчерпания максимума попыток,
  at-least-once.
- **FR-004**: Отдельный процесс-воркер входящих MUST забирать апдейты из
  очереди и доставлять payload без изменений на настроенный внешний
  эндпоинт; обработка запроса вебхука никогда не ждёт доставки.
- **FR-005**: Система MUST атомарно фиксировать доставку апдейта
  (статус delivered) сразу после успешного ответа внешнего сервера.
- **FR-006**: На повторимые сбои доставки (таймаут, обрыв соединения,
  429, 5xx) система MUST отвечать повтором с экспоненциально нарастающей
  задержкой, не создавая лишней нагрузки на временно недоступный
  внешний сервер; на необратимые отказы (остальные 4xx) — переводить
  апдейт в failed без повторов.
- **FR-007**: Система MUST предоставлять CLI-команду регистрации вебхука
  для зарегистрированного бота: система сама генерирует секрет вебхука,
  передаёт его Telegram'у и не раскрывает оператору; парная CLI-команда
  снимает вебхук и останавливает приём.
- **FR-008**: Система MUST хранить секрет вебхука так, чтобы для
  проверки входящих запросов открытый текст не требовался (проверочное
  значение вместо секрета).
- **FR-009**: Запросы вебхука без заголовка секрета или с неверным его
  значением, для незарегистрированного бота или с некорректным телом
  MUST отклоняться без создания каких-либо артефактов в системе.
- **FR-010**: Система MUST вести журнал входящих апдейтов: бот, update_id,
  payload как есть, статус, число попыток, последняя ошибка, время
  приёма и доставки — доступный для эксплуатации теми же средствами, что
  журнал исходящих; все события жизненного цикла апдейта (приём,
  поглощение дубля, попытки доставки, исход) логируются с его
  идентификаторами, включая update_id.
- **FR-011**: Конфигурация доставки (адрес внешнего эндпоинта,
  опциональный auth-заголовок, таймаут запроса) MUST быть частью
  конфигурации системы и меняться без изменения кода.
- **FR-012**: Система MUST поглощать на входе повторную доставку того же
  апдейта — совпадение (бот, update_id, payload) — отвечая Telegram'у
  успехом без создания новой записи; то же update_id с иным содержимым
  MUST приниматься как новый апдейт.
- **FR-013**: Контракт доставки MUST документировать обязанности приёмной
  стороны: успех — только после успешной обработки апдейта;
  дедуплицирование — скользящим окном по (бот, update_id); таймаут
  доставки настраивается с запасом на худшее время обработки приёмником.

### Key Entities *(include if feature involves data)*

- **Входящий апдейт (журнал входящих)**: идентификатор бота; update_id по
  Telegram; payload апдейта без изменений; статус
  (queued/delivering/delivered/failed); число попыток; lease на
  обработку; время следующей попытки; время приёма и доставки; последняя
  ошибка.
- **Регистрация вебхука бота**: связь бота из реестра с секретом приёма
  (в проверочной форме) и признаком активности приёма.
- **Цель доставки**: адрес внешнего эндпоинта обновлений, опциональный
  auth-заголовок, таймаут — системная конфигурация, единая на инстанс.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Ни один апдейт, подтверждённый системой успехом вебхука,
  не теряется при обрушении любого процесса: он либо доставлен внешнему
  серверу, либо виден в журнале как failed с последней ошибкой.
- **SC-002**: Время ответа вебхука не зависит от внешнего сервера: при
  полностью недоступном внешнем сервере приём апдейтов продолжает
  отвечать успехом за то же время, что при доступном; при исправном
  хранилище очереди успешный ответ вебхуку укладывается в 1 секунду.
- **SC-003**: Payload, полученный внешним сервером, побитово совпадает с
  тем, что прислал Telegram, для всех типов апдейтов.
- **SC-004**: При недоступности внешнего сервера в течение 10 минут и
  последующем восстановлении все накопленные за это время апдейты
  доставляются без ручного вмешательства.
- **SC-005**: Доставка at-least-once: повторная доставка возможна только
  в неустранимом окне — крах воркера между успешным POST и фиксацией
  доставки (или гонка конкурентной вставки ретрая); каждый дубль
  идентифицируется парой (бот, update_id) на стороне потребителя.

## Assumptions

- Внешний сервис-владелец ботов один на инстанс; его эндпоинт обновлений
  задаются конфигурацией системы (per-бот маршрутизация — Future
  Enhancements).
- Внешний сервер доступен по сети из системы и рассчитан на дубли
  (дедупликация по update_id на его стороне).
- Регистрация ботов, реестр и хранение токенов уже существуют (фичи
  002/006); эта фича добавляет только приём и доставку апдейтов.
- Публичный адрес вебхуков (домен, TLS-терминация) — внешняя по
  отношению к системе инфраструктура; система использует его при
  регистрации вебхука, но не обслуживает TLS сама.
- Ограничения Telegram на вебхуки (HTTPS, допустимые порты, размер
  payload, лимиты частоты) — внешние и учитываются на этапе плана.
- Исходящий поток (фича 003) не меняется; очередь входящих не влияет на
  очередь исходящих — разные потоки с одинаковыми гарантиями.
- Приёмная сторона (нестабильный сервер) соблюдает контракт доставки:
  успех только после обработки, дедуп скользящим окном по
  (бот, update_id); её реализация — вне этой фичи.
- Исходящий синхронный прокси Telegram API (токен не покидает
  стабильный сервер) — смежная отдельная фича 008, в 007 не входит.
