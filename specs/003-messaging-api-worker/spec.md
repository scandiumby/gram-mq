# Feature Specification: HTTP API приёма сообщений и доставка в Telegram

**Feature Branch**: `003-messaging-api-worker`

**Created**: 2026-10-11

**Status**: Draft

**Input**: User description: "HTTP API приёма сообщений и доставка в Telegram: POST /api/v1/messages с авторизацией X-API-Key; ключи выдаёт CLI на сервере и печатает один раз, в БД только prefix + Argon2id-хэш; сообщение ставится в очередь через BrokerPort (фича 001); отдельный процесс-воркер забирает, отправляет через TelegramSender (aiogram, токен из bots/.env-<bot_slug>, фича 002) и атомарно фиксирует sent + telegram_message_id; повторы 429/сеть через retry брокера, после max_attempts — failed. Подсчёт отправленных — SQL по журналу, без эндпоинтов статистики и дашборда. Health без авторизации."

## Clarifications

### Session 2026-10-11 - MVP-дефолты (автономно, по умолчанию)

Дефолты приняты без вопроса оператору и revisitable: любое изменение —
правкой этой сессии до plan.

- Q: Что отвечает API на сообщение для незарегистрированного бота? → A: 404
  «бот не найден»; реестр — единственный источник истины (контракт
  UnknownBotError брокера), артефактов не создаётся.
- Q: Какой состав payload сообщения в MVP? → A: только текст
  (`text`, plain text без parse_mode и вложений); форматирование и медиа —
  Future Enhancements.
- Q: Нужна ли внешнему сервису идемпотентность/dedup постановки? → A: нет —
  контракт доставки at-least-once документирован (конституция II);
  клиентский dedup-ключ — Future Enhancements.
- Q: Что делает воркер, если у бота нет файла токена или файл повреждён? →
  A: это ошибка отправки на общих основаниях: retry с backoff, после
  max_attempts — failed; специальной ветки нет.
- Q: Где API принимает ключ? → A: только заголовок X-API-Key (конституция
  IV); ключ в query-параметре или теле приравнивается к отсутствию ключа.
- Q: Как в MVP отзывается ключ? → A: поле `revoked_at` проверяется на
  каждом запросе (кэша верификации нет — отзыв действует сразу); CLI
  `key revoke` — Future Enhancements, MVP — эксплуатационный UPDATE по БД.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Выдача API-ключа внешнему сервису (Priority: P1)

Как оператор на сервере, я запускаю `gram-mq key add` и получаю
API-ключ: система генерирует ключ, печатает его в терминал ровно один
раз и сохраняет в базе только префикс и Argon2id-хэш. Я передаю ключ
разработчику внешнего сервиса по защищённому каналу; сам ключ больше
нигде не восстановим.

**Why this priority**: без ключа внешний сервис не имеет доступа к API —
это единственный санкционированный путь машинной аутентификации
(конституция IV); stories 2 и 3 зависят от него.

**Independent Test**: пройти `gram-mq key add`, убедиться, что ключ
напечатан один раз, а в таблице ключей появились prefix и хэш — и не
появился открытый ключ.

**Acceptance Scenarios**:

1. **Given** чистая система, **When** оператор выполняет `gram-mq key
   add`, **Then** ключ напечатан один раз, в базе есть запись с prefix и
   Argon2id-хэшем ключа, и открытый ключ нигде не сохранён.
2. **Given** выданный ключ, **When** его показывают повторно (вывод,
   логи, база), **Then** восстановить ключ из любых артефактов системы
   нельзя.

---

### User Story 2 - Постановка сообщения внешним сервисом (Priority: P1)

Как внешний сервис, я отправляю POST /api/v1/messages с заголовком
X-API-Key и телом {bot_slug, chat_id, text}; система проверяет ключ,
проверяет бота по реестру и ставит сообщение в очередь, отвечая 202 с
идентификатором сообщения. Ответ API никогда не ждёт отправки в
Telegram.

**Why this priority**: это единственная точка входа сообщений в систему;
без неё внешний сервис не может пользоваться прокси.

**Independent Test**: поставить сообщение с валидным ключом (202 + id);
повторить без ключа и с мусорным ключом (401, в журнале ничего не
прибавилось); повторить с неизвестным bot_slug (404) и битым телом
(422).

**Acceptance Scenarios**:

1. **Given** выданный ключ и зарегистрированный бот, **When** сервис
   отправляет валидный запрос, **Then** ответ 202 с идентификатором и в
   журнале появилась строка со статусом «в очереди».
2. **Given** запрос без ключа, с неверным или отозванным ключом,
   **When** система проверяет авторизацию, **Then** ответ 401 без
   деталей причины и без изменения журнала.
3. **Given** запрос с bot_slug, которого нет в реестре, **When** система
   проверяет реестр, **Then** ответ 404, сообщение не ставится.
4. **Given** тело с пустым text, text длиннее лимита Telegram, пустым
   или неформатным chat_id, **When** система валидирует тело, **Then**
   ответ 422, сообщение не ставится.

---

### User Story 3 - Доставка сообщения в Telegram воркером (Priority: P1)

Как получатель в Telegram, я получаю сообщение, поставленное внешним
сервисом: отдельный процесс-воркер забирает сообщение из очереди,
читает токен бота из его файла конфигурации, отправляет текст в чат и
атомарно фиксирует успех — статус «отправлено» и идентификатор
сообщения Telegram одной транзакцией. При отказе сети, лимите 429 или
отсутствии файла токена сообщение вернётся в очередь с задержкой; после
исчерпания попыток — статус «failed» (аварийный журнал).

**Why this priority**: доставка — сама суть системы; at-least-once и
атомарный ack — прямое требование конституции II (NON-NEGOTIABLE).

**Independent Test**: на фейковом отправителе — поставить сообщение,
запустить воркер, убедиться в статусе «отправлено» и идентификаторе
Telegram; уронить воркер между отправкой и подтверждением — после
рестарта сообщение повторно доставлено (дубль в чате допустим) и не
потеряно.

**Acceptance Scenarios**:

1. **Given** сообщение в очереди и рабочий токен бота, **When** воркер
   его обрабатывает, **Then** в одной транзакции записаны статус
   «отправлено» и telegram_message_id.
2. **Given** отправка завершилась сетевой ошибкой или 429, **When**
   воркер обрабатывает отказ, **Then** сообщение вернулось в очередь с
   задержкой (для 429 — не раньше указанного Telegram retry_after) и
   счётчиком попыток +1.
3. **Given** исчерпаны max_attempts, **When** воркер обрабатывает
   последнюю неудачу, **Then** сообщение получает статус «failed» и
   остаётся в журнале как аварийная запись.
4. **Given** воркер остановлен принудительно между отправкой в Telegram
   и подтверждением, **When** воркер перезапущен и аренда истекла,
   **Then** сообщение доставлено повторно — дубль в чате допустим и
   документирован, потери нет.
5. **Given** у бота нет файла токена или файл повреждён, **When** воркер
   берёт сообщение, **Then** это ошибка отправки на общих основаниях:
   retry с backoff, после max_attempts — failed.

---

### User Story 4 - Подсчёт реально отправленных сообщений (Priority: P2)

Как оператор, я считаю количество реально отправленных в Telegram
сообщений одним SQL-запросом к журналу — без эндпоинтов статистики,
дашборда и дополнительных инструментов: статус и метка времени отправки
уже в журнале (фича 001), воркер их честно заполняет (US3).

**Why this priority**: наблюдаемость MVP выбрана сознательно
минимальной — SQL вместо API; полезна сразу после первых доставок.

**Independent Test**: доставить N сообщений US3 и убедиться, что
документированный запрос подсчёта возвращает ровно N.

**Acceptance Scenarios**:

1. **Given** доставленные сообщения, **When** оператор выполняет
   документированный запрос подсчёта по статусу «отправлено», **Then**
   результат равен числу доставленных сообщений (за вычетом прошлых
   прогонов).
2. **Given** сообщения в очереди/повторах, **When** оператор выполняет
   тот же запрос, **Then** недоставленные не учитываются.

---

### Edge Cases

- Запрос с ключом в query-параметре или теле — 401 (только заголовок).
- Отозванный ключ — 401 немедленно, без перезапуска API.
- База недоступна на запросе API — 5xx, сообщение не принято; клиент
  повторяет (частичная недоступность не создаёт полуфабрикатов).
- Два запроса с одним ключом параллельно — оба получают независимые
  ответы; журнал последовательных вставок не теряет ни одну строку.
- Воркер стартовал раньше применения миграций — отказ с понятной ошибкой
  (fail-fast), без молчаливой порчи журнала.
- Убийство API между постановкой в очередь и ответом 202 — клиент не
  получил id, но сообщение в журнале: задокументированный случай
  at-least-once на стороне клиента (повторная постановка создаёт дубль
  доставки — допустимо).
- 429 c retry_after длиннее стандартного backoff — задержка
  уважается.
- Токен бота скомпрометирован/перевыписан — перевыдача и повторная
  регистрация бота (фича 002), старые сообщения в failed/queued
  доотправятся новым токеном после замены файла.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Система MUST предоставлять команду `gram-mq key add`:
  генерация API-ключа, печать в терминал ровно один раз, сохранение в БД
  только prefix и Argon2id-хэша. Открытый ключ MUST NOT сохраняться или
  логироваться системой нигде, кроме однократного вывода.
- **FR-002**: Система MUST предоставлять эндпоинт POST /api/v1/messages:
  авторизация заголовком X-API-Key; запрос без ключа, с неверным или
  отозванным ключом MUST отклоняться 401 без деталей причины; ключ в
  query-параметре или теле авторизацией не считается.
- **FR-003**: Валидный запрос MUST ставить сообщение в очередь через
  контракт брокера (фича 001) и отвечать 202 с идентификатором
  сообщения; идентификатор MUST соответствовать строке журнала.
  Неизвестный bot_slug MUST отклоняться 404 до постановки в очередь.
- **FR-004**: Тело запроса MUST валидироваться форматно: bot_slug —
  непустая строка, chat_id — идентификатор чата Telegram (число со
  знаком или @username — точный формат фиксирует план), text —
  непустая строка не длиннее лимита Telegram (4096 символов). Нарушение
  — 422 без артефактов.
- **FR-005**: Обработка запроса NEVER не ждёт сети Telegram: постановка
  в очередь и ответ — единственная синхронная работа API (конституция
  II: API и воркер — разные процессы).
- **FR-006**: Воркер MUST быть отдельным процессом: забирать сообщения
  арендой (claim), отправлять текст в чат токеном бота из
  `bots/.env-<bot_slug>` и подтверждать успех атомарно — статус
  «отправлено» и telegram_message_id одной транзакцией сразу после
  успешного ответа Telegram.
- **FR-007**: Ошибки отправки (сеть, 429, отсутствие/повреждение файла
  токена, отказ Telegram) MUST обрабатываться retry с backoff:
  счётчик попыток +1, задержка для 429 — не раньше retry_after; после
  max_attempts — статус «failed» с причиной в журнале. Дубликаты
  доставки после разрыва «отправка–подтверждение» допустимы и
  документированы (at-least-once).
- **FR-008**: Токен бота читается только воркером из
  `bots/.env-<bot_slug>` и MUST NOT появляться в логах, HTTP-ответах,
  текстах ошибок и базе; отсутствие файла — ошибка отправки (FR-007),
  не спец-режим.
- **FR-009**: API-ключ MUST NOT появляться в логах, HTTP-ответах и
  текстах ошибок ни целиком, ни фрагментами (кроме короткого prefix в
  административных выводах).
- **FR-010**: Система MUST предоставлять health-эндпоинт без
  авторизации, отвечающий на liveness-запрос; он не раскрывает
  конфигурацию и состояние очередей.
- **FR-011**: Машиночитаемая поверхность ограничена: все маршруты
  /api/v1/* требуют X-API-Key, кроме health; эндпоинты статистики,
  очередей и управления ключами по HTTP отсутствуют (подсчёт — SQL,
  управление ключами — CLI).
- **FR-012**: Журнал сообщений MUST содержать достаточно данных для
  подсчёта доставленных SQL-запросом (статус, метка времени отправки,
  telegram_message_id — схема фичи 001); документированный запрос
  подсчёта входит в quickstart.
- **FR-013**: Эксплуатационные юниты systemd для api и worker MUST
  поставляться (отдельные юниты, env-файл — указателем, без значений;
  конституция Configuration/Stack).
- **FR-014**: Отзыв ключа (revoked_at) MUST действовать на последующих
  запросах без перезапуска API (верификация без кэша в MVP).

### Key Entities *(include if feature involves data)*

- **API-ключ (ApiKey)**: prefix — короткий публичный идентификатор,
  key_hash — Argon2id-хэш, created_at, revoked_at (NULL = действителен).
  Открытого ключа в системе нет (конституция III).
- **Сообщение (Message)**: существует с фичи 001; эта фича заполняет
  отправителем (API) и завершателем (воркер): telegram_message_id,
  sent_at, статусы queued/leased/sent/failed.
- **Файл конфигурации бота** (`bots/.env-<bot_slug>`): источник токена
  для воркера (фича 002); воркер — единственный читатель в runtime.
- **Порты**: BrokerPort (существует), TelegramSender — новый доменный
  порт отправки текста в чат; aiogram — адаптер, фейк — для тестов
  (конституция I).

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Внешний сервис одним HTTP-запросом с выданным ключом
  ставит сообщение и получает 202 с идентификатором; повтор запроса без
  ключа и с мусорным ключом не меняет число строк журнала.
- **SC-002**: После доставки N сообщений (фейковый отправитель в тестах,
  живой бот в quickstart) документированный запрос подсчёта возвращает
  ровно N отправленных; недоставленные (в очереди, повторах, failed) не
  считаются.
- **SC-003**: Принудительная остановка воркера между отправкой и
  подтверждением не теряет сообщение: после рестарта и истечения аренды
  сообщение доставлено повторно (дубль в чате допустим), итоговый статус
  — отправлено.
- **SC-004**: Секретная часть API-ключа и токены ботов отсутствуют в
  логах обоих процессов, дампе БД и HTTP-ответах — воспроизводимая
  grep-процедура по фиксированному прогону не даёт совпадений.
- **SC-005**: Регистрация бота по-прежнему невозможна по HTTP (фича 002,
  SC-004), а все новые маршруты /api/v1/* кроме health требуют ключ:
  матрица проб без ключа закрывает каждый маршрут.

## Assumptions

- MVP-дефолты этой сессии (404 неизвестного бота, только text, без
  dedup, файл токена как обычная ошибка отправки, ключ только в
  заголовке, отзыв через эксплуатационный UPDATE) — приняты автономно и
  revisitable до plan.
- Один внешний сервис-потребитель в MVP: rate limiting и квоты API —
  вне скоупа (Future).
- Один инстанс воркера в MVP (аренда и reclaim контракта брокера уже
  допускают несколько — масштабирование сознательно отложено).
- Живая отправка в Telegram не тестируется автотестами: юнит/контракт —
  на фейковом TelegramSender; живая сквозная проверка — quickstart с
  реальным ботом.
- Argon2id — единственный алгоритм хэширования ключей (конституция III);
  параметры (соль, память/итерации) — решение плана из дефолтов
  библиотеки.
- Формат ключа (длина, алфавит) и длина prefix — решение плана;
  требование спеки: prefix достаточно длинен, чтобы искать запись без
  перебора всех хэшей.
- Валидация chat_id — форматная, локальная; реальное существование чата
  проверяет только Telegram при отправке.
- Подсчёт отправленных — чтение журнала оператором; инструмент
  подключается к той же БД, что и сервисы (схема фичи 001).
- Человеческий realm (OTP, JWT, дашборд) — отдельная будущая фича; эта
  фича его не касается (конституция IV: два realm, здесь только
  машинный).

## Future Enhancements (Post-MVP)

Отложено сознательно (MVP-режим, см. сессию 2026-10-11); каждому пункту
— задача пост-MVP фазы tasks.md и требование в
specs/004-post-mvp-hardening/spec.md (консолидированный бэклог техдолга).

- **CLI управления ключами**: `gram-mq key list` (prefix, даты,
  статус), `gram-mq key revoke <prefix>` — MVP закрывает отзыв
  эксплуатационным UPDATE.
- **Эндпоинт статистики**: глубина очереди и счётчики статусов по
  ботам (queue_depth контракта уже есть) — MVP: SQL.
- **parse_mode и медиа**: форматирование текста, фото, документы — MVP:
  только plain text.
- **Идемпотентность постановки**: клиентский dedup-ключ с окном — MVP:
  at-least-once документирован.
- **Несколько воркеров и конкурирующие потребители** — MVP: один
  инстанс.
- **Rate limiting / квоты API** — MVP: один доверенный потребитель.
