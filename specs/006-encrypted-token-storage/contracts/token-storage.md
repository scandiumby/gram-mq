# Контракт: хранение и склейка токена бота

**Spec**: [spec.md](../spec.md) | **Plan**: [plan.md](../plan.md) |
**Data model**: [data-model.md](../data-model.md)

Единый контракт хранения для трёх сторон: эндпоинт создания (шифрует и
раскладывает), воркер (расшифровывает и склеивает), оператор (интерпретация
файла и строки). Чистая реализация — модуль `token_store.py`; параметры —
[research.md](../research.md) R1–R5.

## Разрез и криптопараметры

```
токен := "<id>:<secret>"           # контракт 002: один ":", числовой id
file_plain := "<id>:<secret[:4]>"   # файловая половина (plaintext до шифра)
db_plain   := "<secret[4:]>"        # табличная половина
pair_nonce := os.urandom(8)         # на каждое создание/перезапись пары
aad        := pair_nonce            # сырые 8 байт, обе половины
half_blob  := hex( nonce_12 ‖ AESGCM(ключ_32, nonce_12, plain, aad) )
ключ        := bytes.fromhex(GRAMMQ_TOKEN_MASTER_KEY)   # 64 hex-символа
```

Расшифровка любой половины с несовпавшим AAD/nonce → `InvalidTag` →
NotReady: подмена между ботами и смешение поколений детектируются локально,
до обращения к Telegram. Склейка: `file_plain ‖ db_plain` + финальная
валидация формата токена.

## Носители

**Файл** `bots/.env-<slug>` (0600, каталог 0700, атомарная запись):

```
GRAMMQ_BOT_NAME=<имя>
GRAMMQ_BOT_FILE_HALF=<half_blob файловой половины>
GRAMMQ_BOT_PAIR_NONCE=<hex nonce_8>
```

**Строка** `gmq_bots`: `token_half = <half_blob табличной половины>`,
`pair_nonce = <hex nonce_8>` — тот же nonce, что в файле.

Старый формат файла (`GRAMMQ_BOT_TOKEN`, plaintext) не распознаётся и не
конвертируется: бот NotReady, пересоздание — через эндпоинт (FR-014).

## Дедуп-скан (при создании)

Для каждого `bots/.env-*`: прочитать, расшифровать файловую половину,
извлечь числовой id. Совпадение с новым токеном:

- строка реестра жива → конфликт (409);
- строки нет → «неполная пара»: обе половины и nonce перезаписываются
  свежими под slug из имени файла, строка + claim_state дописываются
  (лечение повтором, FR-009).

## Разрешение в воркере (порт `BotConfig.token_for → TokenLookup`)

| Состояние | Результат | Дальше в runner |
|---|---|---|
| строки `gmq_bots` нет | `NotRegistered` | permanent: dead_letter «bot not registered» — немедленно |
| файла нет / NULL-колонки / мастер-ключ не задан | `NotReady` | retryable: «bot config unreadable (file/keys)», бэкофф |
| расшифровка/парность/валидация склейки провалились | `NotReady` | retryable (та же причина) |
| всё сошлось | `Ready(token)` | отправка; plaintext — только в памяти процесса |

Инварианты: plaintext токена не покидает память процесса (кэш отправителя
ключуется токеном, как раньше, — сам `Bot`-объект уже держит его внутри,
смена ключа ничего не меняет по существу); причина ошибки никогда не
содержит ни половины, ни nonce (редакция как в `classify` отправителя).

## Порядок записи и отказоустойчивость

Создание: файл → строка + claim_state. Любой сбой до строки оставляет
«файл без строки» — легальное состояние, перехватываемое дедуп-сканом при
повторном POST (см. выше). Ревок: строка бота (транзакция) → файл; строка
claim-леджера сознательно остаётся — claim-ротация итерирует леджер, и
только живая строка доводит очередь отозванного бота до воркера
(dead-letter «bot not registered»); осиротевший файл безвреден (см.
дедуп-скан). Мастер-ключ не задан или потерян: создание — отказ 503;
воркер — NotReady для всех шифрованных ботов (очередь копится в ретраях,
не теряется); восстановление — только перевыпуск токенов через BotFather.
