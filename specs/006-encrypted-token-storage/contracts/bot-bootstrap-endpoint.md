# Контракт: эндпоинты управления ботами (окно бутстрапа)

**Spec**: [spec.md](../spec.md) | **Plan**: [plan.md](../plan.md) |
**Data model**: [data-model.md](../data-model.md)

Административный surface вне обоих authorization realm-ов (прецедент —
`POST /bootstrap/api-key`, spec 005): без аутентификации, доступен только
пока включён флаг окна, секреты приходят исключительно из настроек.

## Настройки окна

| Переменная | Тип | Дефолт | Роль |
|---|---|---|---|
| `GRAMMQ_BOT_BOOTSTRAP_ENABLED` | bool | `false` | включает оба маршрута |
| `GRAMMQ_BOT_BOOTSTRAP_TOKEN` | SecretStr | — | полный токен создаваемого бота |
| `GRAMMQ_TOKEN_MASTER_KEY` | SecretStr | — | мастер-ключ AESGCM половин |

Настройки читаются на старте процесса (снапшот `BotManagement`); смена —
редеплой/рестарт. Операторский цикл: задать токен → включить флаг →
редеплой → операции → выключить флаг и **очистить токен-сеттинг** →
редеплой. Мастер-ключ не очищается (постоянный).

## POST /bootstrap/bots — создание

Запрос: `{"name": "<публичное имя бота>"}` — единственное поле, не секрет;
идентификатор клиент не выбирает.

| Код | Условие | Тело |
|---|---|---|
| 201 | бот создан | `{"status": "created", "bot_slug": "<slug>"}` |
| 422 | имя: пустое / >64 симв. / управляющие (pydantic-схема, как в `/api/v1`) | detail от FastAPI |
| 404 | флаг окна выключен | `{"detail": "not found"}` |
| 409 | токен уже зарегистрирован за живым ботом | `{"detail": "bot token already registered"}` |
| 500 | сбой записи (частичная пара) | `{"detail": "provisioning failed; retry"}` |
| 503 | токен или мастер-ключ не задан/битый | `{"detail": "bootstrap token or master key missing or invalid"}` |

Семантика повторов (идемпотентность результата):

- повтор с тем же токеном после **успеха** → 409 (живой бот найден
  дедуп-сканом);
- повтор после **сбоя посередине** (файл есть, строки нет) → пара
  завершается под прежним slug, ответ 201 с тем же slug;
- конкурентные вызовы → ровно один бот (PK реестра + компенсация).

Slug генерируется системой по действующим правилам 002: последние 4 цифры
числового id токена + два слова словаря; занятость = файл или строка
реестра. В ответе — только факт и slug; никогда: токен, половины, nonce.

## DELETE /bootstrap/bots/{bot_slug} — ревок

Запрос: path-параметр = slug из ответа создания («id бота»).

| Код | Условие | Тело |
|---|---|---|
| 200 | бот отозван | `{"status": "revoked", "bot_slug": "<slug>"}` |
| 404 | флаг выключен; slug неизвестен или уже удалён | `{"detail": "not found"}` |

Успешный ревок: удаляется строка `gmq_bots`, затем файл
`bots/.env-<slug>`. Строка claim-леджера `gmq_bot_claim_state` остаётся
(claim-ротация итерирует её — это то, что доводит очередь отозванного
бота до воркера). Сообщения бота в очереди немедленно уходят в
dead-letter с причиной «bot not registered»; новые
`POST /api/v1/messages` к slug отклоняются как для неизвестного бота (404).
Ротация токена = ревок + создание (новый slug); переключение клиентов —
операторская процедура.

## Инварианты

- Тело запроса создания не содержит секретов; полный токен никогда не
  пересекает HTTP (FR-002/FR-013) — источник только настройка.
- При выключенном флаге оба маршрута отвечают 404 «not found» — как
  несуществующие; никакого материала не обрабатывается.
- Формулировки отказов не различают «не задан» и «битый» (токен, мастер-ключ).
- Логирование: имя/slug и исход операции; никогда — токен, половины,
  nonce-блобы (FR-016).
- Эндпоинты не требуют машинной авторизации (прецедент 005: бутстрап не
  может требовать того, что создаёт); ужесточение `X-API-Key` — опция
  фазы tasks без смены схемы.
