# Feature Specification: Шифрованное распределённое хранение токена бота

**Feature Branch**: `006-encrypted-token-storage`

**Created**: 2026-10-19

**Status**: Implemented (2026-11-21)

**Input**: User description: "AAD — случайный 8-байтовый nonce; первая часть ключа (открытый id + ':' + 4 символа секретной части) хранится зашифрованной в файле бота в bots/, остальная часть — зашифрованной в БД; шифрование AESGCM мастер-ключом из отдельного сеттинга-секрета; создание бота — запросом на API-эндпоинт, закрытый сеттингом-флагом (по умолчанию выключен); полный токен берётся из сеттинга-секрета; при отправке воркер расшифровывает обе части, проверяет nonce и склеивает токен."
Дополнение (2026-10-19): «создавать бота через POST с автоматической генерацией slug (как это было через CLI); ревок — отдельным запросом, снова под сеттингом-флагом, с передачей id бота из ответа на POST создания; CLI-вариант создания ботов выпиливается — в этой схеме он работает некорректно».

## Контекст проблемы

Сейчас полный plaintext-токен бота лежит в `bots/.env-<bot_slug>` (Principle III).
Кража одного файла, бэкапа или снапшота тома даёт злоумышленнику готовый рабочий
токен. На контейнерных деплоях (Amvera, том `/data/bots`) это означает: любой
утёкший снапшот тома или копия каталога — полная компрометация всех ботов.

Решение — разрезать токен на две неполные части и хранить каждую зашифрованной
в своём носителе:

1. **Файловая половина**: открытый числовой id бота + `":"` + первые 4 символа
   секретной части — зашифрована, лежит в файле бота (тот же каталог, что и
   сейчас).
2. **DB-половина**: остаток секретной части — зашифрована, лежит в таблице
   ботов в Postgres.
3. **Шифрование** — аутентифицированное (AESGCM) под выделенным
   мастер-ключом из отдельного сеттинга-секрета, не используемым ни для чего
   другого (в частности, отличным от секретов API-ключей).
4. **AAD обеих половин** — один и тот же случайный 8-байтовый nonce парности;
   он хранится открытым текстом при каждой половине. Несовпадение (подмена
   половины между ботами или смешение поколений при ротации) роняет
   расшифровку локально, до обращения к Telegram.
5. **Создание** — POST-запросом на эндпоинт, закрытый сеттингом-флагом
   (по умолчанию выключен) по образцу spec 005; полный токен сервер берёт
   из сеттинга-секрета панели; slug генерируется системой (как раньше
   делал CLI-визард) и возвращается в ответе — это «id бота» для клиентов
   и для ревока. Plaintext токен не пересекает HTTP.
6. **Ревок** — отдельным запросом под тем же флагом: вход — id бота из
   ответа на создание; бот перестаёт существовать для системы (строка и
   файловая половина удаляются). CLI-путь создания ботов (визард)
   выпиливается: его plaintext-формат в этой схеме мёртв.

Свойства схемы: каждая половина по отдельности бесполезна — даже при утечке
мастер-ключа файл даёт только `id` и 4 символа секрета, БД — секрет без первых
4 символов; компрометация одного носителя (том ИЛИ дамп БД) не даёт рабочего
токена.

**Конституционная база (правка проведена).** Изначально фича конфликтовала
с тремя нормами конституции v2.4.4; правка проведена через
`$speckit-constitution` — действует конституция v3.0.0 от 2026-10-19:

- **Principle III** допускает шифрованные неполные половины токена в обоих
  носителях — файле и БД (аргумент: без мастер-ключа это не секреты — тот
  же принцип, что у `key_hash`);
- **Principle IV** допускает бутстрап-эндпоинт создания бота, выключенный
  по умолчанию и берущий токен из секретной настройки (прецедент —
  эндпоинт активации ключа из spec 005);
- **стандарт Configuration** допускает оконный сеттинг полного токена на
  время операции создания/ротации.

Окончательную оценку соответствия фиксирует Constitution Check на фазе plan.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Создание бота одним POST-запросом с автогенерацией slug (Priority: P1)

Как оператор контейнерного деплоя без shell, я кладу полный токен нового
бота в секретную настройку панели, включаю флаг окна управления ботами,
дожидаюсь применения настроек и «пинаю» эндпоинт создания одним
POST-запросом, передавая в теле только публичное имя бота (не секрет) —
идентификатор я не выбираю. Система генерирует slug по действующим
правилам (как это делал CLI-визард: последние 4 цифры числового id токена
и два слова из словаря, подбор до свободного значения) и раскладывает
токен на две зашифрованные
половины — файловую и табличную — с общим свежим nonce парности. Ответ
подтверждает создание и возвращает slug — единственный «id бота»: по нему
клиенты отправляют сообщения, по нему же позже делается ревок (US3).
После операции я выключаю флаг и очищаю настройку с токеном.

**Why this priority**: входная точка всей схемы; без неё ни половины не
появляются. Тестируется независимо: созданные половины проверяются доставкой
(US2) или прямой расшифровкой мастер-ключом.

**Independent Test**: с настроенными флагом, токеном и мастер-ключом один
запрос создаёт бота; ответ содержит сгенерированный slug; файл бота и строка
таблицы содержат зашифрованные материалы и nonce парности; plaintext токена
в них нет.

**Acceptance Scenarios**:

1. **Given** флаг выключен (значение по умолчанию), **When** оператор «пинает»
   эндпоинт, **Then** создание не происходит, эндпоинт ведёт себя как
   недоступный.
2. **Given** флаг включён, настройка токена и мастер-ключ заданы, **When**
   приходит один запрос создания с именем бота, **Then** генерируется
   уникальный slug, появляются файловая и табличная зашифрованные половины
   с одним nonce парности, ответ подтверждает создание и возвращает slug.
3. **Given** сгенерированный slug совпадает с существующим, **When**
   подбирается идентификатор, **Then** система занимает свободный вариант
   (следующая комбинация слов); коллизия не видна оператору и не требует
   его действий.
4. **Given** флаг включён, но настройка токена пуста или токен невалиден по
   формату, **When** приходит запрос, **Then** отказ с понятной причиной; ни
   файл, ни строка не создаются.
5. **Given** флаг включён, но мастер-ключ не задан, **When** приходит запрос,
   **Then** отказ с понятной причиной; ничего не пишется.
6. **Given** успешное создание, **When** читаются ответ и логи, **Then** в них
   нет ни полного токена, ни какой-либо половины.
7. **Given** токен с этим числовым id уже зарегистрирован за живым ботом,
   **When** приходит повторный запрос создания, **Then** конфликт без
   изменений — второй бот с тем же токеном не создаётся.
8. **Given** прошлое создание оборвалось, оставив половину пары, **When**
   оператор повторяет запрос с тем же токеном, **Then** пара завершается
   под прежним slug, дубликат не возникает.

### User Story 2 - Доставка сообщений ботом с шифрованным хранением (Priority: P2)

Как потребитель очереди, я отправляю сообщения боту, чей токен хранится в
шифрованном виде: воркер при каждом взятии сообщения из очереди читает обе
половины, расшифровывает их, проверяет nonce парности и склеивает токен в
памяти — сообщение уходит в Telegram. Plaintext токен существует только
кратко в памяти воркера. Если расшифровка или проверка парности не проходит,
бот считается «не готовым»: сообщение возвращается в очередь с повтором, а
причина — отличима от ошибок Telegram и не требует к нему обращения.

**Why this priority**: ради этого всё затевалось — доставка работает, а секрета
в покое больше нет. Тестируется независимо на заранее подготовленных
половинах (тестовыми средствами).

**Independent Test**: для бота с корректными половинами сообщение доходит до
Telegram; при порче любой половины сообщение не теряется, а повторяется с
причиной «конфигурация бота не читается».

**Acceptance Scenarios**:

1. **Given** бот с согласованными зашифрованными половинами, **When** сообщение
   попадает в очередь, **Then** оно доставляется, как при старом
   plaintext-хранении.
2. **Given** файловая половина повреждена или подменена, **When** воркер берёт
   сообщение, **Then** расшифровка/проверка парности падает локально: сообщение
   повторяется с отличимой причиной, к Telegram воркер не обращается.
3. **Given** половины от разных поколений токена (nonce парности не совпадает),
   **When** воркер берёт сообщение, **Then** тот же локальный отличимый отказ —
   без обращения к Telegram и без «загадочного» 401.
4. **Given** файловая половина бота отсутствует или нечитаема, **When**
   воркер берёт сообщение, **Then** семантика «бот не готов» (повторяемая
   ошибка) — файл может вернуться. Отсутствующая строка реестра — другой
   случай: бот отозван или неизвестен, сообщение немедленно уходит в
   dead-letter (US3, FR-015).
5. **Given** мастер-ключ в окружении воркера отсутствует или неверен, **When**
   воркер берёт сообщение, **Then** шифрованные боты обрабатываются как «не
   готовые» (повторяемая ошибка), очередь не теряется.

### User Story 3 - Ревок бота отдельным запросом (Priority: P3)

Как оператор, я отзываю бота отдельным запросом под тем же флагом окна
управления: передаю id бота — slug из ответа на создание. Бот перестаёт
существовать для системы: строка таблицы и файловая половина удаляются,
новые сообщения к этому slug отклоняются как к неизвестному боту, а
оставшиеся в очереди сообщения уходят в dead-letter с названной причиной.
Ротация токена складывается из этих же операций: ревок старого бота и
создание нового POST-запросом (новый токен в настройке → новый slug);
переключение клиентов на новый slug — за оператором.

**Why this priority**: завершает жизненный цикл бота без shell; для первого
успешного прохода доставки не требуется.

**Independent Test**: создать бота (US1), поставить сообщение в очередь,
выполнить ревок — сообщение уходит в dead-letter с названной причиной, новые
сообщения к slug отклоняются, файл и строка бота отсутствуют.

**Acceptance Scenarios**:

1. **Given** флаг включён и бот существует, **When** приходит запрос ревока с
   его slug, **Then** строка и файловая половина удаляются, ответ подтверждает
   ревок и не содержит секретов.
2. **Given** в очереди есть сообщения отзываемого бота, **When** выполняется
   ревок, **Then** они не теряются молча: уходят в dead-letter с
   документированной причиной.
3. **Given** бот отозван, **When** клиент отправляет сообщение к его slug,
   **Then** отказ — как для неизвестного бота.
4. **Given** slug неизвестен или бот уже отозван, **When** приходит запрос
   ревока, **Then** отказ без изменений состояния.
5. **Given** флаг выключен, **When** «пинается» эндпоинт ревока, **Then** он
   недоступен, как и эндпоинт создания.

---

### Edge Cases

- Мастер-ключ не задан при включённом флаге → отказ, ничего не пишется (US1,
  сценарий 4).
- Формат токена в настройке невалиден (не ровно один `:`, нечисловой id,
  пустая или короче 4 символов секретная часть) → отказ до любых записей.
- Рассинхрон поколений (файл новый, строка старая — обрыв ротации) → локальная
  отличимая ошибка парности, не 401 Telegram (US2, сценарий 3); лечится
  повторным запросом (US3, сценарий 1).
- Перестановка половин между ботами → ошибка парности локально (AAD-привязка).
- Оператор не очистил настройку токена и не выключил флаг → окно остаётся
  открытым; пока настройка не очищена, полный токен живёт в secret store
  панели — документируемый residual-риск, процедура требует очистки (как в
  spec 005).
- Рестарт процесса в окне операции → настройки читаются на старте; после
  рестарта окно остаётся открытым, пока флаг включён (цикл 005).
- Потеря мастер-ключа → все шифрованные боты «не готовы»; восстановление —
  только перевыпуск токенов через BotFather. Документируемый риск; ротация
  мастер-ключа (перешифровка) вне скоупа фичи.
- Файл старого plaintext-формата (создан до этой фичи) → бот «не готов»:
  старый формат не читается, бот пересоздаётся новым путём; автоматической
  конвертации и переходного периода нет — прод-деплой ботов ещё не
  используется.
- Имя бота в запросе пустое, длиннее 64 символов или содержит управляющие
  символы → отказ до любых записей; имя — публичная метка в файле бота,
  slug от него не зависит (идёт от числового id токена).
- Конкурентные запросы создания с одним токеном → выживает один бот,
  без дубликатов и смешанных пар половин.
- Ревок бота с непустой очередью → сообщения уходят в dead-letter с
  причиной, а не исчезают молча.
- Сетевой сбой в момент запроса создания → оператор просто повторяет вызов;
  идемпотентность гарантирует согласованное состояние.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: В настройках ДОЛЖЕН существовать флаг окна управления ботами,
  включающий эндпоинты создания и ревока; значение по умолчанию — выключено;
  пока флаг выключен, оба эндпоинта недоступны и не выполняют никаких
  действий.
- **FR-002**: В настройках ДОЛЖНА существовать секретная настройка полного
  токена без значения по умолчанию — единственный источник plaintext на
  сервере в окно операции. Запрос создания НЕ несёт секретных данных:
  plaintext токен никогда не пересекает HTTP.
- **FR-003**: Эндпоинт ДОЛЖЕН раскладывать валидный токен на две части:
  файловую (числовой id + `":"` + первые 4 символа секретной части) и
  табличную (остаток секретной части).
- **FR-004**: Обе части ДОЛЖНЫ шифроваться аутентифицированным шифрованием
  AESGCM под выделенным мастер-ключом токенов — отдельной секретной
  настройкой, не используемой ни для каких иных секретов (включая секреты и
  материал активации API-ключей); мастер-ключ не имеет значения по умолчанию.
- **FR-005**: Для каждой пары половин ДОЛЖЕН генерироваться случайный
  8-байтовый nonce парности, применяемый как AAD при шифровании обеих половин
  и хранимый открытым текстом при каждой из них; расшифровка ДОЛЖНА
  завершаться отказом при несовпадении nonce — подмена половины между ботами
  или поколениями детектируется локально, без обращения к Telegram.
- **FR-006**: Файловая половина ДОЛЖНА записываться атомарно с правами
  «только владелец» (действующие нормы файла 0600 и каталога 0700
  сохраняются).
- **FR-007**: Табличная половина и её nonce парности ДОЛЖНЫ храниться в
  существующей таблице ботов (через миграцию схемы); plaintext секретного
  материала в БД отсутствует.
- **FR-008**: Эндпоинт создания ДОЛЖЕН принимать от клиента только публичное
  имя бота (не секрет) и НЕ ДОЛЖЕН принимать идентификатор: slug генерирует
  система по действующим правилам генерации (последние 4 цифры числового id
  токена + два слова словаря; подбор свободного значения при коллизии) и
  возвращает его в ответе.
- **FR-009**: Повторная регистрация токена с числовым id уже живого бота
  ДОЛЖНА завершаться конфликтом без изменений состояния; при обнаружении
  неполной пары половин (наследие оборванного создания) повторный вызов с тем
  же токеном ДОЛЖЕН завершать пару под прежним slug, не создавая дубликат.
  Конкурентные вызовы не оставляют смешанных пар половин.
- **FR-010**: Ответ об успехе ДОЛЖЕН содержать подтверждение и slug бота (его
  «id») и НЕ ДОЛЖЕН содержать полный токен или любую из половин.
- **FR-011**: При включённом флаге, но невалидной/отсутствующей настройке
  токена, непригодном для slug имени или отсутствующем мастер-ключе эндпоинт
  ДОЛЖЕН отказывать с понятной причиной, ничего не записывая.
- **FR-012**: Воркер при доставке ДОЛЖЕН читать обе половины, расшифровывать
  их, проверять nonce парности и склеивать токен только в памяти; при сбое
  расшифровки или парности бот обрабатывается как «не готовый» (повторяемая
  ошибка с отличимой причиной), обращение к Telegram не происходит.
- **FR-013**: Plaintext токен НЕ ДОЛЖЕН оказываться в HTTP-трафике, логах,
  ответах API, БД и файлах хранения; в покое он существует только в
  настройке-источнике в окно операции и кратко в памяти процесса.
- **FR-014**: Воркер НЕ ДОЛЖЕН читать старый plaintext-формат файлов: бот с
  plaintext-файлом обрабатывается как «не готовый» (повторяемая ошибка);
  пересоздание бота — через эндпоинт создания.
- **FR-015**: Ревок ДОЛЖЕН выполняться отдельным эндпоинтом под тем же
  флагом: вход — slug (id) из ответа на создание; успешный ревок удаляет
  строку бота и файловую половину; сообщения этого бота в очереди уходят в
  dead-letter с названной причиной; новые сообщения к slug отклоняются как
  для неизвестного бота; ревок неизвестного или уже отозванного бота
  отказывает без изменений состояния.
- **FR-016**: События создания, ревока и отказов ДОЛЖНЫ логироваться без
  секретов — без токена, половин и nonce-материалов.
- **FR-017**: Существующие CLI-команды создания и управления ботами (визард и
  его plaintext-запись) ДОЛЖНЫ быть удалены: единственный путь создания и
  ревока бота — эндпоинты этой фичи.
- **FR-018**: Конституционная база фичи — действующая конституция v3.0.0
  (правка от 2026-10-19 уже проведена): Principle III допускает шифрованные
  неполные половины токена, Principle IV — выключаемый по умолчанию
  бутстрап-эндпоинт управления ботами, стандарт Configuration — оконный
  сеттинг полного токена. Реализация идёт в рамках этих норм; дополнительных
  правок конституции не требуется.

### Key Entities *(include if feature involves data)*

- **Бот (существующая сущность, расширяется)**: `bot_slug` — генерируется
  системой при создании (клиент его не выбирает), служит единственным «id
  бота»; добавляются табличная зашифрованная половина токена и её nonce
  парности.
- **Файловая половина токена (новый артефакт)**: зашифрованный блоб
  (id + `:` + 4 символа секрета), шифровальный nonce и nonce парности;
  живёт в файле бота рядом с именем бота.
- **Nonce парности**: случайные 8 байт, открытый текст при обеих половинах,
  AAD шифрования; идентификатор поколения пары.
- **Мастер-ключ токенов (новая настройка)**: секрет без значения по умолчанию;
  отдельный от всех существующих секретов.
- **Настройка полного токена (новая настройка)**: секрет на окно операции
  создания/ротации; очищается после операции.
- **Флаг окна управления ботами (новая настройка)**: булев переключатель
  доступности эндпоинтов создания и ревока; не секрет, по умолчанию выключен.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Оператор деплоя без shell создаёт работающего бота, используя
  только локальную выдачу токена, настройки панели и один HTTP-запрос с
  публичным именем бота; slug генерируется системой и возвращается в ответе;
  вся процедура укладывается в несколько минут.
- **SC-002**: В состоянии покоя полный plaintext-токен отсутствует в файлах,
  БД, логах и ответах — проверяемо инспекцией и тестами; каждый носитель в
  отдельности не содержит материала, достаточного для использования токена,
  даже при известном злоумышленнику мастер-ключе.
- **SC-003**: Компрометация любого одного носителя — тома файлов или дампа
  БД — не позволяет отправлять сообщения от имени бота.
- **SC-004**: Скорость доставки сообщений не деградирует ощутимо относительно
  plaintext-хранения: накладные расходы на расшифровку неотличимы от шума
  сетевого вызова Telegram (доля времени доставки, приходящаяся на
  криптографию, — менее 0,1%).
- **SC-005**: Отозванный бот полностью перестаёт обслуживаться: новые
  сообщения к его slug отклоняются, оставшаяся очередь уходит в dead-letter с
  причиной, строка и файловая половина удалены — проверяемо тестами и
  инспекцией.

## Assumptions

- Алгоритм и параметры зафиксированы заказчиком и не выбор фазы plan: AESGCM;
  разрез токена после 4-го символа секретной части; AAD = случайный
  8-байтовый nonce парности. Кодирование блобов, имена переменных окружения,
  URL эндпоинта и структура файлов — решения фазы plan.
- Мастер-ключ отдельный от `GRAMMQ_KEY_BOOTSTRAP_MATERIAL` и всех секретов
  API-ключей; используется только шифрованием половин токенов. Ротация
  мастер-ключа (перешифровка всех половин) — вне скоупа v1.
- Аутентификация запросов создания и ревока — только флаг (прецедент
  spec 005: создание ничего секретного не несёт, материал берётся из
  настройки; ревок несёт только публичный slug). Фаза plan может ужесточить
  до требования действующего `X-API-Key`.
- Настройки читаются на старте процесса: смена флага, токена или мастер-ключа
  требует редеплоя/рестарта — штатный цикл панели (как в 005).
- Окно процедуры: операции создания/ревока → флаг выключен, настройка токена
  очищена. Пока настройка не очищена, полный токен живёт в secret store
  панели — документируемый residual-риск.
- Потеря мастер-ключа делает все шифрованные ботов «не готовыми»;
  восстановление — только перевыпуск токенов через BotFather и повторное
  создание половин. Документируется в quickstart.
- Контекст деплоя — один контейнер api+worker (Amvera): общее окружение и
  общий том `/data/bots`, поэтому мастер-ключ доступен обоим процессам без
  дополнительной инфраструктуры.
- Правка конституции проведена до реализации: v2.4.4 → v3.0.0 (MAJOR —
  переопределение норм двух принципов и одного стандарта), 2026-10-19;
  Principle III и IV теперь допускают шифрованные половины и
  бутстрап-эндпоинт, Configuration — оконный сеттинг полного токена (FR-018).
  Допуск «CLI-визарда» в Principle IV после выпиливания (FR-017) становится
  неиспользуемым — это не конфликт; убирается PATCH-правкой, когда станет
  мешать.
- «Id бота» в ответе создания и запросе ревока — это `bot_slug`: числовой id
  токена зашифрован в половинах и ключом поиска служить не может.
- Дедуп по числовому id токена выполняется на момент создания: сервер
  расшифровывает файловые половины (мастер-ключ у него есть) и блокирует
  регистрацию только за живым ботом; после ревока id свободен для новой
  регистрации.
- Имя бота приходит в теле запроса создания (публичное, не секрет);
  онлайн-проверка токена у Telegram при создании (getMe) не вводится — она
  конфликтовала бы с Principle II («HTTP-запрос не ждёт Telegram»);
  невалидный токен проявится первым же 401 при доставке. Фаза plan может
  вернуться к этому вместе с отдельной правкой нормы для окна бутстрапа.
- Ревок — жёсткое удаление (строка + файловая половина): шифрованный
  материал не должен переживать отозванного бота. Soft-вариант (`revoked_at`
  как у API-ключей) — за фазой plan, если понадобится аудит.
- Ротация токена = ревок старого бота + создание нового (новый slug);
  переключение клиентов на новый slug — операторская процедура,
  документируется в quickstart.
