# Research: Шифрованное распределённое хранение токена бота

**Date**: 2026-10-19 | **Spec**: [spec.md](spec.md) | **Plan**: [plan.md](plan.md)

Фаза 0. Все решения приняты по конституции v3.0.0, кодовой базе
(`token.py`, `wizard.py`, `slug.py`, `broker.py`, `runner.py`,
`bot_config.py`, миграции 0001–0002) и зафиксированным требованиям спеки
(FR-001–FR-018). NEEDS CLARIFICATION в спеке отсутствуют — здесь они
сводятся в проектные решения с отвергнутыми альтернативами.

## R1. Криптобиблиотека и алгоритм

**Decision**: `cryptography` (pyca), класс `AESGCM`; ключ 32 байта,
шифровальный nonce — 12 байт `os.urandom` на каждую половину.

**Rationale**: AESGCM даёт аутентифицированное шифрование одним вызовом
(`encrypt(nonce, data, aad)`), не требует ручной склейки tag/HMAC; пакет
Rust/OpenSSL-backed, типизирован (mypy --strict), ставится manylinux-wheel
в `python:3.12-slim` без системных пакетов. CPU-цена расшифровки ~50 байт —
единицы микросекунд (AES-NI): на фоне Telegram-вызова и DB round-trip'ов
доля < 0,1% (SC-004), уровень кеша `_bot_cache` не меняется.

**Alternatives**: (а) `Fernet` из того же пакета — проще API, но нет AAD:
перестановка шифртекстов между ботами расшифровывалась бы успешно, а
nonce парности пришлось бы проверять вручную поверх — хуже при той же
зависимости; (б) `PyCryptodome` — лишняя зависимость при уже имеющемся
`cryptography` в экосистеме aiogram; (в) свой XOR/KDF — исключено
конституционно-методологически: только библиотечные примитивы.

## R2. Мастер-ключ: формат и поведение при отсутствии

**Decision**: `GRAMMQ_TOKEN_MASTER_KEY` — hex 64 символа (32 байта),
`SecretStr | None = None`. Парсинг ленивый, на использовании: невалидный
hex/длина — трактуется как «ключ не задан» (единое поведение с материалом
бутстрапа 005: одна формулировка отказа для «нет» и «битый», без подсказок).

**Rationale**: Отдельный от всех прочих секретов (FR-004) и постоянный —
в отличие от оконных `BOT_BOOTSTRAP_*`; `None` законен на деплое без
шифрованных ботов, поэтому fail-fast на старте невозможен: последствия
вместо этого определены поведением — эндпоинт создания отказывает (503,
FR-011), воркер маркирует шифрованных ботов NotReady (FR-012, retryable —
очередь не теряется). Генерация: `python -c "import os;print(os.urandom(32).hex())"`.

**Alternatives**: (а) обязательный ключ с abort на старте — ломает деплои
без ботов и тесты; (б) base64 вместо hex — без разницы, hex короче для
панели; (в) несколько ключей с версионированием (ротация мастер-ключа) —
вне скоупа v1 (assumption спеки), формат блоба допускает префикс версии
в задачах-фазе.

## R3. AAD = nonce парности: генерация и хранение

**Decision**: `os.urandom(8)` на каждое создание/перезапись пары; hex-16
символов хранится открыто и в файле бота, и в строке `gmq_bots.pair_nonce`;
AAD вызова — сырые 8 байт (не hex). Обе половины пары шифруются с одним и
тем же AAD; несовпадение (подмена между ботами, смешение поколений) роняет
расшифровку локально (`InvalidTag`).

**Rationale**: Требование заказчика (AAD = случайный 8-байтовый nonce);
заменяет более раннюю идею «AAD = slug‖half‖pair_id» — открытый nonce в
обоих носителях решает и парность поколений, и подмену между ботами без
дополнительных полей: чужая пара половин не сойдётся ни по файлу, ни по
строке. Открытость значения безопасна: это идентификатор, не секрет.

**Alternatives**: (а) AAD = slug + метка половины без nonce — не ловит
смешение поколений одного бота (главный сценарий FR-009); (б) HMAC от
полного токена в строке — добавляет колонку и вторую проверку, не давая
ничего сверх AEAD-тега.

## R4. Разрез токена

**Decision**: файловая половина (plaintext до шифрования) = `"{id}:{secret[:4]}"`;
табличная = `secret[4:]`. Склейка = конкатенация расшифрованных половин +
финальная `validate_token_format` (ровно один `:`, числовой id, непустой
секрет) как санити-чек.

**Rationale**: Зафиксировано заказчиком; секретная часть Telegram-токена
≥ 30 символов, поэтому «секрет[:4] + остаток» гарантированно непусты.
Каждая половина в одиночку бесполезна даже при известном мастер-ключе
(файл — id и 4 символа; БД — секрет без первых 4), SC-002/SC-003.

**Alternatives**: разрез ровно по `:` (id | весь секрет) — отклонён ранее
в обсуждении спеки: файловая половина становилась бы полноценным секретом.

## R5. Формат файла `bots/.env-<slug>`

**Decision**: dotenv-стиль сохраняется, ключи меняются:

```
GRAMMQ_BOT_NAME=<имя>
GRAMMQ_BOT_FILE_HALF=hex( nonce_12 ‖ AESGCM(nonce_12, file_plain, aad) )
GRAMMQ_BOT_PAIR_NONCE=hex16
```

Запись атомарная (tmp + `os.replace`), права 0600, каталог 0700 —
проверка/создание каталога наследуются от `_check_bots_dir` визарда.
Чтение старого формата (`GRAMMQ_BOT_TOKEN` с plaintext) невозможно:
парсер его не распознаёт → бот NotReady (FR-014), пересоздание — эндпоинтом.

**Rationale**: hex — один алфавит для бинарных блобов, самодостаточная
строка без base64-паддинга; `os.replace` поверх O_EXCL визарда, потому что
эндпоинт обязан перезаписывать файл при лечении неполной пары (FR-009),
а O_EXCL создан для однократного создания. Имя бота остаётся в файле —
публичная метка оператора (в БД не дублируется).

**Alternatives**: (а) JSON-файл — ломает преемственность dotenv-контракта
002; (б) отдельный файл для nonce — второй файл на бота без выгоды;
(в) держать имя в БД — колонка ради метки, файл остаётся единственным
местом операторского контекста.

## R6. Эндпоинты и настройки окна

**Decision**: `POST /bootstrap/bots` (body `{"name": str}`, 201 →
`{"status": "created", "bot_slug": str}`) и `DELETE /bootstrap/bots/{slug}`
(200 → `{"status": "revoked"}`); оба вне realm-пространств, гейт —
`GRAMMQ_BOT_BOOTSTRAP_ENABLED` (bool, false), полный токен —
`GRAMMQ_BOT_BOOTSTRAP_TOKEN` (SecretStr | None). Именование параллельно
005 (`KEY_BOOTSTRAP_*`). Коды: 404 — флаг выключен (и для неизвестного
slug при ревоке); 400 — невалидное имя (пустое/длиннее 64/управляющие —
правила `_validate_name` визарда); 409 — токен уже зарегистрирован за
живым ботом; 503 — токен/мастер-ключ не заданы или битые (одна
формулировка); 500 — сбой записи (оператор повторяет — идемпотентность
лечит). В API-домене — порты `BotProvisioner` / `BotRevoker` (callables)
+ снапшот `BotManagement(enabled, token)`; сборка DB/FS-адаптеров —
`api/main.py`.

**Rationale**: Прямое масштабирование прецедента 005: третий
административный surface, дефолт-выключен, секреты только через настройки.
DELETE с path-параметром вместо POST-тела ревока: идемпотентный по смыслу
ресурсный жест, slug — не секрет и в URL не течёт ничего чувствительного.

**Alternatives**: (а) ревок через POST `/bootstrap/bots/revoke` —
эквивалентно, но изобретает глагол при наличии DELETE; (б) токен в теле
запроса вместо настройки — запрещён спекой (FR-002: plaintext не
пересекает HTTP); (в) требование `X-API-Key` на окно — отложено в
assumptions (plan может ужесточить без смены схемы).

**Уточнение (2026-11-21, implement)**: невалидное имя даёт **422**, а не
400 — валидация живёт в pydantic-схеме `BotCreateIn`, единообразно с
остальным API; контракт `bot-bootstrap-endpoint.md` обновлён.

## R7. Slug: переиспользование действующих правил

**Decision**: `generate_bot_slug` из `cli/slug.py` переезживает в
`src/gram_mq/slug.py` (вместе с `dune_words.py`) без изменений алгоритма:
`<last4 числового id>-<слово1>-<слово2>`, SystemRandom, до 50 попыток;
`is_taken` = файл `.env-<slug>` существует ИЛИ строка реестра. Числовой id
эндпоинт знает из токена настройки. Имя бота на slug не влияет (поправка
спеки на фазе plan: действующие правила — от id токена, не от имени).

**Rationale**: FR-008 требует действующих правил; переезд модуля —
следствие выпиливания CLI-пакета (FR-017): единственный потребитель — API.
Slug содержит последние 4 цифры id — уже публичная величина (та же
норма 002).

**Alternatives**: транслитерация имени — никогда не была правилом 002,
породила бы новую коллизионную семантику.

## R8. Дедуп и идемпотентность создания

**Decision**: Перед созданием — скан `bots/.env-*`: каждая файловая
половина расшифровывается мастер-ключом, извлекается числовой id.
Совпал id и строка реестра жива → 409. Файл есть, строки нет (оборванное
создание) → пара завершается под slug из имени файла: обе половины и nonce
перезаписываются свежими, строка и claim-state дописываются. Конкурентные
POST: PK реестра закрывает гонку (IntegrityError → компенсация/конфликт,
прецедент визарда). Порядок записи: файл → строка реестра + claim-state.

**Rationale**: FR-009; numeric id больше нигде не лежит открыто, скан —
единственный способ дедупа; O(файлов) при десятках ботов — миллисекунды.
Лечение повтором делает процедуру оператора одношаговой при любом сбое
посередине.

**Alternatives**: (а) хранить числовой id открыто в строке бота — утечка
половины файла в БД, ломает SC-002; (б) не детектить и дублировать —
повтор оператора после неясного ответа плодил бы ботов; (в) таблица
«id→slug» — та же открытость id, плюс сущность.

## R9. Ревок и снятие FK `gmq_messages → gmq_bots`

**Decision**: Ревок в одной DB-транзакции удаляет `gmq_bot_claim_state`
(дети FK) и `gmq_bots`, затем файловая половина сносится unlink'ом
(провал unlink не откатывает ревок: осиротевший файл перехватит дедуп
как «неполная пара» и перезапишется при следующем создании того же
токена). Миграция `0003` снимает FK `fk_gmq_messages_bot_slug_gmq_bots`:
журнал — историческая запись, переживающая бота; вместо FK `enqueue`
делает явный `SELECT EXISTS(gmq_bots)` → `UnknownBotError` → 404
(поведение API неизменно). Гонка «ревок между проверкой и INSERT»
документирована: сообщение попадёт в очередь и будет отвалидировано
воркером как NotRegistered → dead-letter.

**Rationale**: Существующий enqueue полагается на IntegrityError FK
(broker.py:101) — с жёстким ревоком FK непригоден: строка бота не может
быть удалена, пока в журнале есть хоть одна ссылка (даже sent/failed).
Явная проверка сохраняет контракт `UnknownBotError` и 404 хендлера.
Удаление claim-state обязательно: claim итерирует его (001).

**Alternatives**: (а) soft-ревок `revoked_at` — отклонён спекой
(assumption: шифрованный материал не переживает бота) и порождает
политику воскрешения; (б) оставить FK и отказывать в ревоке при непустом
журнале — ревок зависел бы от истории навсегда; (в) `ON DELETE SET NULL`
— `bot_slug NOT NULL` в журнале, потеря контекста сообщения.

**Уточнение (2026-11-21, implement)**: интеграционный прогон вскрыл
дефект этого решения: `claim` итерирует леджер `gmq_bot_claim_state`, и
его удаление при ревоке делало очередь бота навсегда незахватываемой.
Исправление: миграция `0003` снимает и FK `gmq_bot_claim_state →
gmq_bots`; ревок удаляет только строку `gmq_bots` и файл; строка
леджера, как и журнал, — историческая запись, переживающая бота, и
именно она доводит очередь до воркера (dead-letter через
`NotRegistered`). Массовый дед-леттер из ревока отверг: гонки с
`leased`-строками у воркера. Подробности — заметка в plan.md.

## R10. Эволюция порта `BotConfig` и семантика воркера

**Decision**: `token_for(bot_slug) -> TokenLookup`, где `TokenLookup` =
`Ready(token)` | `NotRegistered` | `NotReady`. Адаптер `SplitFileBotConfig`
(bots_dir + session_factory + master_key): нет строки реестра →
NotRegistered; строка есть, но файла нет/расшифровка или парность
провалились/мастер-ключ не задан → NotReady. Runner: NotRegistered →
permanent dead_letter «bot not registered» (немедленно — бот не
«вернётся»); NotReady → retryable с отличимой причиной «bot config
unreadable (file/keys)». Старое поведение «файл отсутствует = retryable»
сохраняется для живых ботов (файл может вернуться).

**Rationale**: FR-012/FR-015; различение необходимо, чтобы ревок не
мучил очередь ~часом ретраев (20 попыток × бэкофф до 300с) перед
dead-letter'ом. Порт меняется под нужду адаптера — конституционный путь
(I); in-memory fake для тестов обновляется вместе с портом.

**Alternatives**: (а) оставить `str | None` и проверять реестр в runner
отдельным портом — два запроса и размазанная логика; (б) exception-based
(специальные исключения из адаптера) — исключения как поток управления
для ожидаемого состояния.

## R11. Выпиливание CLI-визарда

**Decision**: Удаляются `cli/wizard.py`, `cli/token.py`, подкоманды
`bot add`/`bot list` и их exit-коды (контракт 002 объявляется устаревшим
вместе с plaintext-форматом); `cli/main.py` остаётся точкой входа
`key add`/`key prepare`. Валидация формата токена и файловый формат
переезжают в `token_store.py`; реестр — в `adapters/postgres/bot_registry.py`;
slug — в `src/gram_mq/slug.py`. Тесты визарда удаляются, тесты slug
переносятся.

**Rationale**: FR-017: plaintext-путь мёртв (воркер его не читает),
поддерживать два формата файлов — долг навсегда; «structure decision» —
код движется к единственному живому потребителю.

**Alternatives**: держать визард для локальной разработки — он writes
plaintext, который воркер не примет: сломанный UX вместо отсутствующего.

## R12. Проверка токена у Telegram при создании

**Decision**: Не делаем (assumption спеки): синхронный `getMe` из API
нарушил бы Principle II; невалидный токен проявится 401 на первой
доставке → dead-letter с классифицированной причиной.

**Rationale**: Бутстрап-окно не должен зависеть от доступности Telegram;
валидность формата проверяется локально до записей (FR-011).

**Alternatives**: (а) getMe с PATCH-правкой нормы для окна — возможное
будущее усиление, вне скоупа; (б) фоновая проверка воркером после
создания — сущность «статус проверки» и race с первой отправкой.

## R13. Безопасность процессов и остаточные риски

**Decision**: Задокументированы в quickstart: (1) полный токен живёт в
secret store панели, пока `GRAMMQ_BOT_BOOTSTRAP_TOKEN` не очищен — окно
обязательно закрывается; (2) потеря `GRAMMQ_TOKEN_MASTER_KEY` = все
шифрованные боты NotReady навсегда, восстановление — перевыпуск токенов
в BotFather; (3) компрометация панели/env контейнера = компрометация
токенов (single-container residual — защита схемы ат-рест: том ИЛИ дамп
БД по отдельности бесполезны).

**Rationale**: Спеки SC-002/SC-003 и assumptions; фиксируем границу
заявленной защиты, чтобы не переоценить её при эксплуатации.
